## 1. 용어부터 정확하게 — 데이터 레이스와 경쟁 조건은 다르다

면접에서 이 둘을 섞어 쓰면 바로 감점된다.

**데이터 레이스(data race)**: 다음 네 조건이 동시에 성립하는 상태. C++ 표준에서 **정의되지 않은 동작(undefined behavior)**이다.
1. 둘 이상의 스레드가
2. **같은 메모리 위치**에 접근하고
3. 그중 **최소 하나가 쓰기**이고
4. 그 접근들 사이에 **동기화(happens-before 관계)가 없다**

**경쟁 조건(race condition)**: 실행 순서(타이밍)에 따라 결과가 달라지는 **논리적 결함**. 데이터 레이스가 없어도 발생할 수 있다. 예를 들어 락으로 잘 보호된 "잔액 확인 → 출금" 두 연산 사이에 다른 스레드가 끼어들면, 데이터 레이스는 없지만 경쟁 조건은 있다.

이 프로젝트의 Bug #1은 **데이터 레이스**였다. 두 스레드가 같은 `std::cout` 버퍼에 동기화 없이 썼다.

## 2. `WorkerQueue` — 80줄짜리 코드를 줄마다 설명할 수 있어야 한다

이 프로젝트에서 사용자가 직접 도입한 동시성 구조는 이것 하나다. 그래서 **면접에서 가장 확실하게 나올 코드**다.

```cpp
void WorkerQueue::Push(std::function<void()> job)
{
    {
        std::lock_guard<std::mutex> guard(_mutex);
        _jobs.push(std::move(job));
    }
    _cv.notify_one();
}

void WorkerQueue::WorkerLoop()
{
    while (true)
    {
        std::function<void()> job;
        {
            std::unique_lock<std::mutex> lock(_mutex);
            _cv.wait(lock, [this]() { return _stop || !_jobs.empty(); });

            if (_jobs.empty())
                return;

            job = std::move(_jobs.front());
            _jobs.pop();
        }
        job();
    }
}
```

설명해야 할 포인트가 여섯 개 있다.

**① 락의 범위가 왜 중괄호로 좁혀져 있는가**
`Push`에서 `notify_one()`은 락 **바깥**에서 부른다. 락을 쥔 채로 깨우면, 깨어난 워커가 곧바로 그 락을 다시 잡으려다 실패하고 또 자는 낭비(hurry-up-and-wait)가 생길 수 있다. `WorkerLoop`도 `job()` 실행을 락 바깥에서 한다. **작업 실행 중에 락을 쥐고 있으면 그동안 다른 스레드가 `Push`조차 못 한다.** 이게 이 구조에서 가장 중요한 한 줄이다.

**② `_cv.wait`에 왜 조건(predicate)을 넘기는가**
`condition_variable`은 **가짜 깨어남(spurious wakeup)**이 허용된다. 아무도 깨우지 않았는데 깨어날 수 있다. 그래서 `wait` 반환 후 조건을 반드시 다시 확인해야 하고, 조건을 인자로 넘기는 형태(`wait(lock, pred)`)가 그 재확인 루프를 대신해준다. 조건 없이 `wait(lock)`만 쓰면 버그다.

**③ `wait`가 락을 어떻게 다루는가**
`wait`는 (1) 락을 풀고 (2) 잠들고 (3) 깨어나면 락을 **다시 잡은 뒤** 반환한다. 이 원자적인 "풀고-자기"가 없으면, 락을 풀고 자려는 사이에 온 알림을 놓치는 lost wakeup이 발생한다.

**④ 가시성(visibility)까지 보장되는 이유**
`std::queue`는 스레드 안전이 아니지만, 여기서는 안전하다. mutex의 unlock은 release, lock은 acquire 의미를 가지므로 **Push 스레드가 락을 놓기 전에 한 모든 쓰기는, 그 락을 잡은 워커 스레드에 반드시 보인다**(happens-before). "락은 배타성만 주는 게 아니라 메모리 가시성도 준다"는 점을 말할 수 있으면 좋다.

**⑤ 소멸자의 종료 프로토콜**
```cpp
WorkerQueue::~WorkerQueue()
{
    { std::lock_guard<std::mutex> guard(_mutex); _stop = true; }
    _cv.notify_one();
    _worker.join();
}
```
`_stop`을 락 안에서 세팅하는 이유는, 워커가 조건을 검사하는 시점과 겹쳐도 안전해야 하기 때문이다. 그리고 `WorkerLoop`는 `_stop`이 켜져도 **큐가 빌 때까지 계속 소비한다**(`if (_jobs.empty()) return;`). 즉 남은 작업을 버리지 않고 끝낸다. 메트릭 저장 큐이므로 이 선택이 맞다.

**⑥ 멤버 선언 순서**
```cpp
std::mutex _mutex;
std::condition_variable _cv;
std::queue<std::function<void()>> _jobs;
bool _stop = false;
std::thread _worker;   // 반드시 마지막
```
멤버는 선언 순서대로 생성된다. `_worker`가 마지막이므로, 스레드가 시작될 때 mutex·큐·플래그는 이미 전부 초기화되어 있다. **`_worker`를 맨 위에 선언하면 초기화되지 않은 멤버를 새 스레드가 건드리는 레이스가 생긴다.** 헤더에 주석으로 이미 적혀 있는 내용이니 그대로 설명하면 된다.

### 꼬리 질문 — "왜 스레드 풀이 아니고 전용 스레드 1개인가?"
> "SQLite는 writer가 하나뿐이라는 제약이 있고, 메트릭은 시계열이라 순서대로 들어가면 충분합니다. 워커를 여러 개 두면 SQLite 쪽에서 락 경합이 생기거나 순서가 섞이기만 하고 이득이 없습니다. 단일 워커는 '큐 안에서는 항상 직렬'이라는 성질을 공짜로 주므로, 이 용도에는 이게 맞는 선택이었습니다."

## 3. 락 없이 안전하게 만드는 방법 — 스레드 한정(thread confinement)

이 프로젝트에서 **락을 쓰지 않고도 안전한 부분**이 있다. 이유를 설명할 수 있어야 한다.

`Collector/main.cpp`의 `pendingMetrics`(아직 Console로 안 보낸 메트릭 목록)는 두 곳에서 쓰인다.
- 메트릭 수신 핸들러: `pendingMetrics.push_back(pkt);`
- `flushToWebServer`: 목록을 읽고 비운다

락이 하나도 없는데 안전하다. **둘 다 `io_context` 스레드에서만 실행되기 때문**이다. `cliThread`(표준 입력을 읽는 별도 스레드)는 `flushToWebServer`를 직접 부르지 않고 이렇게 넘긴다.

```cpp
asio::post(ioContext, flushToWebServer);
```

`asio::post`는 "이 작업을 `io_context`를 돌리는 스레드에서 실행해달라"는 요청이다. 즉 **공유 데이터에 락을 거는 대신, 그 데이터를 만지는 코드를 항상 같은 스레드로 모은다.** 이것이 스레드 한정이고, "락이 없다"가 "생각을 안 했다"가 아니라 **의도된 설계**임을 보여주는 지점이다.

같은 패턴이 반대 방향으로도 쓰인다. 저장 워커 스레드 안에서:

```cpp
metricStoreQueue.Push([storePtr, pkt, &ioContext, &broadcastServer]()
{
    storePtr->Store(pkt);
    asio::post(ioContext, [&broadcastServer]() { broadcastServer.Notify(); });
});
```

`broadcastServer`는 Asio 소켓을 들고 있어서 `io_context` 스레드에서만 만져야 한다. 그래서 워커 스레드에서 직접 부르지 않고 `asio::post`로 되돌려 보낸다. **"저장이 실제로 끝난 뒤에 알림"이라는 순서와, "소켓은 io_context 스레드에서만"이라는 제약을 동시에 만족시키는 구조**다.

> **면접 요약 한 줄**: "공유 상태에 락을 거는 방법과, 공유 상태를 한 스레드에 가두는 방법 두 가지가 있는데, 이 프로젝트는 데이터 성격에 따라 둘을 나눠 썼습니다. 큐로 넘기는 작업은 mutex, Asio 자원은 스레드 한정입니다."

### 참고: `strand`
Asio에는 `strand`라는 도구가 있다. `io_context`를 여러 스레드로 돌리면서도 특정 핸들러 그룹만 직렬 실행을 보장하는 장치다. **이 프로젝트는 `io_context`를 단일 스레드로 돌리기 때문에 `strand`가 필요 없었다.** "왜 strand를 안 썼나요?"라는 질문에는 이렇게 답하면 되고, 반대로 "io_context를 멀티스레드로 확장한다면?"이라는 질문에는 "그때는 strand가 필수가 된다"고 답하면 된다.

## 4. `Lock.cpp` — 스핀락을 비트 단위로 읽기

Round 2에서 크래시를 낸 그 코드다. 지금은 수정되어 있으므로, **버그가 있던 상태와 지금 상태를 모두 설명**할 수 있어야 한다.

### 비트 레이아웃 (`Lock.h`)
```
[WWWWWWWW][WWWWWWWW][RRRRRRRR][RRRRRRRR]   ← atomic<uint32> _lockFlag
 상위 16비트 = 쓰기 락을 가진 스레드 ID     (WRITE_THREAD_MASK = 0xFFFF0000)
 하위 16비트 = 읽기 락을 잡은 스레드 수     (READ_COUNT_MASK  = 0x0000FFFF)
```
하나의 32비트 원자 변수에 두 가지 상태를 욱여넣은 구조다. 읽기-쓰기 락(다수 읽기 허용, 쓰기는 배타)을 이 한 변수로 구현한다.

### 쓰기 락 획득 (`WriteLock`)
```cpp
const uint32 threadId = GetThisThreadId();
const uint32 lockThreadId = (_lockFlag.load() & WRITE_THREAD_MASK) >> 16;

if ((threadId & 0xFFFF) == lockThreadId)   // 이미 내가 가진 락 → 재진입
{
    _writeCount++;
    return;
}
// ...
uint32 expected = EMPTY_FLAG;
if (_lockFlag.compare_exchange_strong(expected, desired))   // CAS
{
    _writeCount++;
    return;
}
```

설명 포인트 세 가지.
- **CAS(compare-and-swap)**: "지금 값이 비어 있으면(EMPTY_FLAG) 내 스레드 ID로 바꿔라"를 한 번의 원자적 연산으로 한다. 실패하면 남이 먼저 잡은 것이다.
- **재진입(reentrant) 처리**: 소유자가 같으면 카운트만 올리고 통과한다. 그래서 `_writeCount`가 필요하다. `_writeCount`는 원자 변수가 아닌데도 안전한데, **그 시점의 소유 스레드만 건드리기 때문**이다. 소유권이 넘어가는 것 자체가 `_lockFlag`에 대한 원자 연산(CAS와 store, 기본 메모리 순서는 seq_cst)을 통해 일어나므로, 이전 소유자가 쓴 `_writeCount` 값은 다음 소유자에게 happens-before로 보인다. **비원자 변수를 원자 변수가 만든 순서 관계 뒤에 숨기는 패턴**이고, 4장의 mutex 가시성(2장 ④)과 같은 원리다.
- **스핀 후 타임아웃**: 5,000번 스핀하고(`MAX_SPIN_COUNT`), 10초(`ACQUIRE_TIMEOUT_TICK = 10000`)가 지나면 `CRASH("LOCK_TIMEOUT")`. **데드락을 조용히 매달려 있게 두지 않고 일부러 죽이는 설계**다. 게임 서버 프레임워크의 관례이고, Round 2의 "10초 만에 크래시"가 정확히 이 지점이었다.

### 스핀락 vs 뮤텍스 (반드시 구분)
| | 스핀락(`Lock`) | 뮤텍스(`std::mutex`) |
|---|---|---|
| 대기 방식 | CPU를 태우며 계속 재시도 | 커널에 재워달라고 요청(`futex`) |
| 적합한 상황 | 임계 구역이 매우 짧을 때 | 임계 구역이 길거나 블로킹 작업을 포함할 때 |
| 이 프로젝트 | 게임 서버용, 짧은 락 전제 | `WorkerQueue` — 안에서 SQLite `fdatasync`까지 도는 긴 작업 |

**왜 `WorkerQueue`에 mutex가 맞았나**를 이렇게 설명할 수 있다. 저장 작업은 디스크 flush를 포함해 밀리초 단위로 걸리므로, 그 시간을 스핀으로 태우는 것은 CPU 낭비다. 스핀락은 임계 구역이 나노초~마이크로초일 때만 이득이다.

### 버그의 정체
포팅 과정의 복사·붙여넣기 실수로, **`ReadLock()`의 본문이 `WriteUnlock()` 자리에 들어갔다.** 그래서 `WriteUnlock()`이라는 이름 아래 실제로는 `_lockFlag.fetch_add(1)`(읽기 카운트 증가)이 들어 있었고, 원래 있어야 할 해제 로직은 사라졌다. 정확히 말하면 서로 맞바꿔치기된 게 아니라 **한쪽이 다른 쪽을 덮어쓴 형태**다 — `ReadLock()`은 헤더에 선언만 남고 `.cpp`에는 정의 자체가 없었다. 아무도 부르지 않아 링크 에러조차 나지 않은 채 숨어 있었다(2026-08-05에 원본과 `diff`를 떠서 둘 다 복원).

```cpp
// 지금(수정 후) — 원본 로직
void Lock::WriteUnlock(const char* name)
{
    if ((_lockFlag.load() & READ_COUNT_MASK) != 0)
        CRASH("INVALID_UNLOCK_ORDER");

    const int32 lockCount = --_writeCount;
    if (lockCount == 0)
        _lockFlag.store(EMPTY_FLAG);   // ← 소유 스레드 ID 비트를 지우는 이 줄이 사라져 있었다
}
```

**왜 그때까지 아무도 몰랐나**가 이 이야기의 핵심이다.
- 소유 스레드 ID 비트가 안 지워지면, **같은 스레드**가 다시 락을 잡을 때는 재진입 분기를 타고 그냥 통과한다. 아무 문제가 없어 보인다.
- **다른 스레드**가 그 락을 잡으려 하면 `_lockFlag`가 영원히 비어 있지 않으므로 CAS가 계속 실패하고, 10초 후 `CRASH("LOCK_TIMEOUT")`.
- 이 프로젝트는 Round 2에서 처음으로 이 큐를 **크로스 스레드로** 썼다(네트워크 스레드가 `Push`, 워커 스레드가 `Execute`). 그 순간 버그가 드러났다.

> **면접 답변 요약**: "여러 프로젝트에서 검증됐다는 말은 '검증된 사용 패턴에서 안전하다'는 뜻일 뿐, 새로운 사용 패턴까지 보장하지 않습니다. 이 락은 단일 스레드 경로에서만 쓰여 왔고, 제가 처음으로 크로스 스레드로 쓰면서 드러났습니다. 나중에 원본과 `diff`를 떠서 포팅 중 함수 본문이 뒤바뀐 실수라는 걸 확정하고 복원했습니다."

## 5. `std::cout`은 스레드 안전한가 — Bug #1의 정확한 원리

이 질문은 정확한 답을 아는 사람이 드물어서, 제대로 답하면 인상적이다.

**표준이 보장하는 것**: `std::cout`처럼 C stdio와 **동기화된(synchronized)** 표준 스트림 객체에 여러 스레드가 동시에 써도 **데이터 레이스는 발생하지 않는다.** 내부적으로 stdio의 락이 관여하기 때문이다.

**표준이 보장하지 않는 것**: 출력 **순서와 섞임**. 데이터 레이스가 없다는 것과 "한 줄이 온전하게 나온다"는 것은 전혀 다른 보장이다. 여러 `<<` 연산은 각각 독립적인 호출이라, 락이 있어도 다른 스레드의 출력이 중간에 끼어들 수 있다.

**`sync_with_stdio(false)`를 켜면**: C stdio와의 동기화를 끊어 성능을 얻는 대신, **위의 "데이터 레이스가 없다"는 보장 자체가 사라진다.** 이게 Bug #1이다.

정리하면 이 프로젝트에서 일어난 일은 이렇다.
1. 성능을 위해 `sync_with_stdio(false)`를 켰다 → 안전장치가 사라졌다
2. 메트릭 로그만 워커로 옮기고, `accept` 로그 등 4곳은 네트워크 스레드에 남겼다 → 두 스레드가 같은 스트림에 썼다
3. 실제 데이터 레이스 발생 → 진단 로그가 문자 단위로 뒤섞여 나왔다
4. 해결: 남은 출력도 전부 같은 워커로 위임 → **"런타임 중 스트림을 만지는 스레드는 정확히 하나"** 원칙

4번은 3장의 **스레드 한정과 똑같은 해법**이다. 락을 추가한 게 아니라, 만지는 주체를 하나로 줄였다. 이 연결을 말할 수 있으면 설계를 이해한 것으로 들린다.

### 꼬리 질문 — "그냥 로그마다 mutex를 걸면 안 되나요?"
> "가능하지만 두 가지가 나빠집니다. 첫째, 락을 잡는 쪽이 네트워크 스레드라면 로그를 쓰는 동안 네트워크 처리가 멈춥니다. 애초에 그 블로킹을 없애려고 워커로 옮긴 거라 목적이 상충합니다. 둘째, 출력 순서는 여전히 보장되지 않습니다. 반면 큐로 넘기면 네트워크 스레드는 즉시 돌아가고, 워커가 순서대로 출력하니 로그 순서까지 정리됩니다."

## 6. 캡처와 수명 — 비동기 코드에서 가장 많이 나는 사고

작업을 다른 스레드로 넘기면 **그 작업이 실행되는 시점에 원본이 살아있는지**가 항상 문제가 된다.

**값으로 복사해야 하는 경우** (이 프로젝트가 실제로 그렇게 한 두 곳)
```cpp
metricStoreQueue.Push([storePtr, pkt, ...]() { storePtr->Store(pkt); });   // pkt: 값 복사
```
`pkt`은 수신 핸들러의 파라미터(참조)라 핸들러가 끝나면 사라진다. 워커가 나중에 실행하므로 반드시 복사해야 한다.

```cpp
std::string errMsg = ec.message();   // ec는 콜백 스코프 밖에서 죽을 수 있음
consoleLogQueue.Push([errMsg]() { std::cerr << ... << errMsg << '\n'; });
```

**참조로 캡처해도 되는 경우**
`storePtr`, `&ioContext`, `&broadcastServer`는 `main()` 스코프에 살아 있고, 워커 스레드는 `main()`이 끝나기 전에 정리되므로 안전하다 — **라는 것이 코드의 전제다.** 그런데 여기에 구멍이 하나 있다.

### 작성 중 발견해 실제로 고친 잠재 결함 (2026-09-29)
`Collector/main.cpp`의 선언 순서는 **원래** 이랬다.

```
store            (51행)
metricStoreQueue (56행)   ← 워커 큐
consoleLogQueue  (61행)   ← 워커 큐
pendingMetrics   (65행)
ioContext        (67행)   ← 워커 큐보다 뒤!
broadcastServer  (71행)
```

C++은 스코프를 벗어날 때 **선언의 역순으로** 소멸시킨다. 따라서 소멸 순서는 `broadcastServer` → `ioContext` → ... → `consoleLogQueue` → `metricStoreQueue` → `store`다.

문제는 `metricStoreQueue`의 소멸자가 **남은 작업을 다 비우고** 끝난다는 점이다. 그 작업 안에는 이런 코드가 있다.

```cpp
asio::post(ioContext, [&broadcastServer]() { broadcastServer.Notify(); });
```

즉 **이미 소멸된 `ioContext`에 post하는 경로가 이론적으로 존재한다.**

다만 **당시 실제로는 발생하지 않았다.** `ioContext.run()`이 끝나지 않는 무한 루프이고 Collector는 시그널로 종료되므로, `main()`의 스코프 종료 경로 자체에 도달하지 않는다(소멸자가 아예 호출되지 않는다).

**수정 완료(2026-09-29)**: `asio::io_context ioContext;` 선언을 두 `WorkerQueue` 선언보다 **위로** 옮겼다. 새 소멸 순서는 `broadcastServer` → `pendingMetrics` → `consoleLogQueue` → `metricStoreQueue` → `ioContext` → `store`이므로, 워커 큐가 남은 job을 비우는 시점에 `ioContext`와 `store`가 모두 살아 있다.

여기서 한 단계 더 따져볼 것이 있다. 새 순서에서는 `broadcastServer`가 워커 큐보다 **먼저** 소멸한다. 그런데도 안전한 이유는, 드레인 중 실행되는 `asio::post`가 핸들러를 큐에 넣기만 하고, 그 핸들러를 실행할 주체(`run()`을 도는 스레드)가 이미 없기 때문이다. `io_context`는 소멸할 때 미실행 핸들러를 그냥 파괴하므로 `broadcastServer` 참조가 역참조되는 일이 없다. **"참조가 죽었다"와 "죽은 참조를 실제로 쓴다"는 다르다**는 점을 구분할 수 있으면 이 종류의 질문에 강해진다.

검증: 빌드 성공, `ctest` 18/18 통과. 선언 위치 이동뿐이라 동작·성능·실측 수치는 전부 그대로다(코드 전문은 `Docs/SESSION_LOG.md` 2026-09-29 항목).

면접에서 "종료 처리는 어떻게 하셨나요?"라는 질문이 나오면 이렇게 답할 수 있다.
> "현재 Collector는 시그널로 종료되는 구조라 정상 종료 경로가 없습니다. 그래서 `WorkerQueue`는 소멸자에서 큐를 비우고 `join`하도록 만들어 뒀지만 실제로는 호출되지 않습니다. 그런데 코드를 다시 보다가, 선언 순서상 `io_context`가 워커 큐보다 먼저 소멸하게 되어 있는 걸 발견했습니다. 워커 큐 소멸자가 남은 작업을 비울 때 그 작업이 `io_context`에 post를 하기 때문에, 정상 종료 경로가 생기는 순간 use-after-free가 되는 구조였습니다. 지금은 도달하지 않는 경로였지만 선언 순서만 바꿔서 미리 막아뒀습니다."

**"스스로 찾아서 고친 잠재 결함"은 면접에서 값이 가장 높은 종류의 답변이다.** 기능 요구사항이 아니라 수명 관리를 스스로 따져봤다는 증거이기 때문이다.

### `cliThread.detach()`
표준 입력을 읽는 스레드는 `detach()`된다. `std::cin`에서 블로킹되어 있어 `join()`으로 회수할 방법이 없기 때문이다. **detach된 스레드가 참조하는 자원은 프로세스가 끝날 때까지 살아 있어야 한다**는 제약이 따라온다. 여기서는 프로세스 종료 = 프로그램 종료이므로 성립한다.

## 7. 이 프로젝트의 동시성 구조 요약 — 외울 표

**Collector 스레드 4개** (`CODE_ARCHITECTURE.md` §2와 동일)
| 스레드 | 하는 일 | 공유 상태 보호 방식 |
|---|---|---|
| 메인 (`io_context`) | accept, TLS 핸드셰이크, recv, 타이머 | `pendingMetrics`를 스레드 한정으로 독점 |
| 워커 1 (`metricStoreQueue`) | `Store()` (SQLite, `fdatasync` 포함) | mutex + condition_variable 큐 |
| 워커 2 (`consoleLogQueue`) | `cout`/`cerr` 조립·출력 | 동일. **런타임 중 스트림 단독 소유자** |
| `cliThread` (detach) | `std::cin` 블로킹 read | 직접 처리 안 하고 `asio::post`로 위임 |

**동시성 사고 3건과 해법**
| 사고 | 원인 | 해법 |
|---|---|---|
| `LOCK_TIMEOUT` 크래시 (Round 2) | `Lock::WriteUnlock`이 소유 스레드 비트를 안 지움 | 표준 라이브러리만 쓰는 `WorkerQueue`로 대체. 나중에 원본과 diff로 원인 규명·복원 |
| `cout` 데이터 레이스 (Round 5) | `sync_with_stdio(false)` + 두 스레드가 같은 스트림 | 모든 출력을 한 워커로 위임 |
| futex 경합 57% (Round 4) | 워커 1→2개, 메트릭마다 `notify_one()` | 미해결. 배칭·락프리 큐·수평 확장이 후보 (1편 4장) |
| 소멸 순서 잠재 결함 (2026-09-29) | `ioContext`가 워커 큐보다 뒤에 선언 → 드레인 중 소멸된 `ioContext`에 post | `ioContext` 선언을 워커 큐보다 위로 이동 |

## 8. 예상 질문과 답변

### Q1. 데이터 레이스와 경쟁 조건의 차이가 뭔가요?
> "데이터 레이스는 두 스레드가 같은 메모리에 동기화 없이 접근하고 그중 하나가 쓰기인 상태로, C++에서는 정의되지 않은 동작입니다. 경쟁 조건은 실행 순서에 따라 결과가 달라지는 논리 결함이라 락을 제대로 걸어도 생길 수 있습니다. 제가 겪은 `cout` 문제는 전자였습니다."

### Q2. `condition_variable`에 조건을 왜 같이 넘기나요?
> "가짜 깨어남이 허용되기 때문입니다. 아무도 깨우지 않았는데 `wait`가 반환될 수 있어서, 깨어난 뒤 조건을 반드시 다시 확인해야 합니다. 조건을 넘기는 형태는 그 재확인 루프를 표준이 대신 해주는 것이고, `wait(lock)`만 쓰면 버그입니다."

### Q3. `notify_one()`을 락 안에서 부르면 안 되나요?
> "동작은 합니다. 다만 락을 쥔 채 깨우면 깨어난 스레드가 곧바로 그 락을 잡으려다 실패하고 다시 대기할 수 있어서 불필요한 컨텍스트 스위치가 생깁니다. 그래서 큐에 넣는 구간만 락으로 감싸고 알림은 락 바깥에서 보냅니다."

### Q4. `std::queue`는 스레드 안전하지 않은데 왜 안전한가요?
> "mutex가 배타성만 주는 게 아니라 메모리 가시성도 주기 때문입니다. unlock이 release, lock이 acquire 의미를 가지므로 Push 스레드가 락을 놓기 전에 한 쓰기는 그 락을 잡은 워커 스레드에 반드시 보입니다. 큐 접근이 전부 이 락 안에 있으니 안전합니다."

### Q5. `pendingMetrics`에는 락이 없는데 안전한가요?
> "네, 그 데이터를 만지는 코드가 전부 `io_context` 스레드에서만 실행되기 때문입니다. 표준 입력을 읽는 별도 스레드는 직접 만지지 않고 `asio::post`로 `io_context` 스레드에 작업을 넘깁니다. 락을 거는 대신 공유 상태를 한 스레드에 가두는 방식이고, 스레드 한정이라고 부릅니다."

### Q6. 왜 스핀락이 아니라 `std::mutex`를 쓰셨나요?
> "워커가 하는 일이 SQLite 저장이라 디스크 flush까지 포함해 밀리초 단위로 걸립니다. 그 시간을 스핀으로 태우면 CPU만 낭비합니다. 스핀락은 임계 구역이 나노초 단위로 짧을 때만 이득이고, 그 반대 상황이라 커널에 재워달라고 요청하는 mutex가 맞았습니다."

### Q7. `LOCK_TIMEOUT` 크래시는 정확히 무엇이었나요?
> "그 프레임워크의 락은 32비트 원자 변수 하나에 상위 16비트는 쓰기 락 소유자 스레드 ID, 하위 16비트는 읽기 락 카운트를 넣는 구조입니다. 그런데 포팅 과정에서 `WriteUnlock`과 `ReadLock`의 본문이 뒤바뀌어서, 언락할 때 소유자 ID 비트를 지우는 코드가 사라졌습니다. 같은 스레드가 다시 잡을 때는 재진입으로 통과하니 문제가 안 보이는데, 다른 스레드가 잡으려 하면 CAS가 영원히 실패해서 10초 스핀 후 의도적으로 크래시하는 설계에 걸렸습니다. 제가 처음으로 이 큐를 크로스 스레드로 쓰면서 드러났습니다."

### Q8. 왜 그 락을 직접 고치지 않고 새 큐를 만들었나요?
> "그 코드는 다른 프로젝트들이 함께 쓰는 공용 코어라, 원인을 확신하지 못한 상태에서 건드리면 영향 범위가 제 프로젝트를 넘어갑니다. 그래서 제 저장소 안에서 표준 라이브러리만 쓰는 80줄 남짓(헤더 35줄 + 구현 47줄)의 작은 큐로 대체하고 문제를 먼저 해결했습니다. 그 뒤에 원본 소스와 `diff`를 떠서 포팅 실수라는 원인을 규명하고 복원했습니다."

### Q9. `std::cout`은 스레드 안전한가요?
> "조건부입니다. C stdio와 동기화된 상태에서는 데이터 레이스가 일어나지 않는다고 표준이 보장하지만, 출력이 섞이지 않는다는 보장은 아닙니다. 그리고 `sync_with_stdio(false)`를 켜면 그 데이터 레이스 방지 보장 자체가 없어집니다. 저는 성능을 위해 그걸 켜놓고 두 스레드에서 출력을 하고 있어서 실제 레이스가 발생했습니다."

### Q10. 그 레이스를 어떻게 발견했나요?
> "우연에 가깝습니다. 100-agent 구간에서 워커 분리가 실제로 적용됐는지 확인하려고 스레드 ID를 로그에 찍었는데, 그 진단 로그 자체가 문자 단위로 뒤섞여서 나왔습니다. 레이스를 찾으려던 도구가 레이스의 증거가 된 셈입니다. 이 경험 때문에 지금은 멀티스레드 코드에서 `cout` 진단 자체를 신뢰하지 않게 됐습니다."

### Q11. 비동기로 넘긴 작업에서 수명 관리는 어떻게 하셨나요?
> "실행 시점에 원본이 살아있는지를 기준으로 캡처 방식을 나눴습니다. 패킷이나 에러 메시지처럼 핸들러 스코프가 끝나면 사라지는 값은 복사하고, `main()` 스코프에 살아 있는 저장소나 `io_context`는 참조로 캡처했습니다. 다만 참조 캡처는 소멸 순서까지 따져야 안전한데, 실제로 그걸 다시 점검하다가 워커 큐가 `io_context`보다 먼저 선언되어 있는 걸 발견했습니다. 소멸이 역순이라 워커 큐가 남은 작업을 비울 때 이미 소멸된 `io_context`에 post하게 되는 구조였습니다. 시그널 종료라 도달하지 않는 경로였지만, 선언 순서를 바꿔서 고쳐뒀습니다."

### Q12. `io_context`를 멀티스레드로 돌릴 생각은 없었나요?
> "고려했지만 이번에는 안 했습니다. 스레드를 늘리면 핸들러가 동시에 실행되므로, 지금 락 없이 쓰고 있는 `pendingMetrics` 같은 공유 상태에 전부 보호가 필요해지고, Asio의 `strand`로 직렬화 구간을 다시 설계해야 합니다. 병목이 CPU가 아니라 디스크 대기였기 때문에, 그 상황에서 스레드를 늘리는 건 원인 해결이 아니라 문제를 복잡하게 만드는 선택이라고 판단했습니다. 실제로 저장을 떼어낸 것만으로 100-agent 하드 리밋이 풀렸습니다."
