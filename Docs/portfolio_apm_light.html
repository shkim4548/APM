// Architecture

전체 시스템 구조

Agent → Collector(로컬 저장) → APM_Console(웹 대시보드)까지 3개 프로세스, 구간별 별도 키를 쓰는 2개의 AES-256-GCM 암호화 구간.

[ Agent ] [ Collector ] ResourceCollector ─ CPU/메모리/디스크/네트워크/TCP Linux: /proc, /proc/net/dev, TCP_INFO Windows: GetSystemTimes, GlobalMemoryStatusEx, GetIfTable2, SIO_TCP_INFO │ Protobuf 직렬화 (apm::Metric) ▼ [PacketHeader{size,id}] ← 프레이밍 (ApmSession::ProcessAccumulated) │ AesGcmPayload::Seal() — AES-256-GCM (AEAD) ▼ ─────────────────────── TLS (asio::ssl) ─────────────────────── ──────────────── 비동기 I/O 코어 (asio::io_context) ──────────────── │ PacketHandler ─ 타입 안전 디스패치 │ IMetricStore ─ SQLite / TimescaleDB (컴파일 타임 선택) │ ResilientSender ─ 단절 시 큐잉 → 재연결 시 순서대로 재전송 │ AesGcmPayload::Seal() — AES-256-GCM (AEAD) ▼ ──── TLS (Collector↔Console 전용 인증서) ──── [ APM_Console — ApmConsole.Host (.NET 8) ] MetricsReceiverService (TcpListener + SslStream) │ PacketHeader 파싱 → AesGcm 복호화 → Metric.Parser.ParseFrom ▼ ApmDbContext (SQLite, webserver_apm.db) 저장 │ MetricsHub (SignalR, /apm/hub/metrics) 실시간 브로드캐스트 ▼ 브라우저 /apm/dashboard ─ Chart.js 그래프 5개 + 최근 메트릭 표(11컬럼)
// Agent ↔ Collector
AES-256-GCM (agent_collector_aes.key)
원래는 KISA 표준 국산 블록 암호(ARIA-256-CBC+HMAC, Encrypt-then-MAC)를 실무처럼 다뤄보는 목적으로 구현·검증까지 마쳤으나, 이후 AES-GCM으로 통일(아래 "설계 의사결정" 참고) — 구현 경험 자체는 코드·문서로 남아있다.
// Collector ↔ Console
AES-256-GCM (webserver_aes.key)
.NET 진영과의 상호운용성과 AEAD의 구조적 이점(패딩 오라클 공격면 자체가 없음)을 위해 채택. 두 구간 모두 IPayloadSealer 인터페이스로 추상화되어 있어 세션은 암호 방식을 모르고, 키는 구간별로 분리되어 있다.
// How The Numbers Are Actually Computed

지표 수집 — OS 커널에서 직접

ResourceCollector(C++, Linux)가 /proc 파일시스템·소켓 옵션을 직접 파싱해서 지표를 만든다 — 라이브러리 뒤에 숨지 않고 계산 방식 하나하나를 직접 결정했다.

지표소스핵심 포인트
CPU 사용률 /proc/stat 부팅 이후 누적 jiffies라 한 시점 값만으론 의미 없음 — 두 샘플 사이의 델타로 계산. iowait도 idle에 합산(표준 관례).
메모리 사용량 /proc/meminfo MemFree가 아니라 MemAvailable 사용 — 아래 상세 참고.
네트워크 대역폭 /proc/net/dev 인터페이스별 누적 바이트를 델타 계산, steady_clock으로 실제 경과시간 측정(고정 주기 가정 안 함). lo(루프백)는 제외.
TCP 연결 품질 getsockopt(TCP_INFO) RTT/재전송/혼잡윈도우를 애플리케이션이 재측정하지 않고 커널이 이미 추적 중인 값을 그대로 조회 — 아래 상세 참고.
디스크 사용량 statvfs() POSIX 표준 함수로 블록 수×블록 크기를 바이트로 환산.
// MemFree가 아니라 MemAvailable
Linux는 남는 메모리를 페이지 캐시로 적극 활용한다 — MemFree(완전 여유분)만 보면 "메모리가 거의 다 찼다"는 착시가 생긴다. MemAvailable은 캐시처럼 필요시 즉시 회수 가능한 부분까지 커널이 직접 계산해 제공하는 값 — 실제 체감 여유 메모리에 훨씬 가깝다.
// TCP 품질을 왜 커널 값으로 조회하나
커널의 TCP 스택은 흐름/혼잡 제어를 위해 RTT·재전송 횟수를 이미 실시간으로 추적하고 있다. getsockopt(fd, IPPROTO_TCP, TCP_INFO, ...)로 그 값을 그대로 읽어오면 되는데, 애플리케이션이 별도로 재측정하면 정확도는 떨어지고 오버헤드만 늘어난다. TLS 아래 순수 TCP 계층 정보라 암호화 여부와 무관하게 조회 가능.
// Running, Not Just Built

실제 실행 화면

Collector+Console을 함께 띄우고 실 트래픽을 흘려 직접 촬영(2026-07-29) — 4개 화면 전부 실제 데이터.

/apm/dashboard Chart.js 그래프 5개(CPU/메모리/디스크/네트워크/TCP RTT) + SignalR 실시간 갱신, 최근 메트릭 표 11컬럼.
/apm/alerts 임계치 편집 + 활성 알림 목록. 실제로 임계치를 낮춰 알림이 열리고 렌더링되는 것까지 실 트래픽으로 확인 완료.
/apm/traces 시간 창(1h/24h/7d) 전환 가능한 p50/p95/p99 백분위 통계 — 실제 span 데이터로 렌더링 확인.
터미널 — Agent / Collector / LoadTester jiffies 델타 CPU%, MemAvailable 기반 메모리, TCP_INFO RTT 등 실측값이 실제로 콘솔에 찍히는 모습 + 300-agent 부하 테스트 실행 로그.
// Design Decisions

설계 의사결정

각 선택의 이유 — "왜 이렇게 만들었는가".

// 01
Standalone Asio 채택
문제 기존 서버는 Windows IOCP에 강하게 결합되어 있어 Linux 등 다른 OS에서 전혀 동작하지 않았다.
판단 OS별 비동기 I/O 메커니즘(IOCP/epoll)을 직접 분기하는 대신, 이를 추상화해 제공하는 Standalone Asio(Boost 전체 의존 없이)를 채택 — 비동기 I/O·멀티스레드 구조 자체는 기존 설계 유지.
해결 Linux에서 빌드+실행까지 검증(포트 리스닝, 무크래시) — 실무 서버 환경(Linux 다수)에 즉시 적용 가능한 크로스플랫폼 네트워크 계층 확보.
// 02
ApmSession 독립 작성 (공용 Session 무수정)
문제 공유 Session 클래스에 TLS를 가상 함수로 수술하면, TLS를 쓰지 않는 다른 소비자까지 영향을 받는다.
판단 TLS 소비자가 하나뿐인 시점에 공용 클래스 책임을 넓히는 건 과설계(YAGNI) — 독립된 ApmSession을 신규 작성.
해결 Session은 완전 무수정, ApmSession이 메시지 프레이밍·페이로드 암호화·재연결까지 전담.
// 03
ARIA-CBC+HMAC → AES-GCM 마이그레이션
문제 Agent↔Collector는 ARIA-256-CBC+HMAC(Encrypt-then-MAC, 구현·검증 완료)을 썼는데, 수동 조합이라 순서를 잘못 짜면 패딩 오라클이 재발할 여지가 있고, 자동 테스트도 AES-GCM에만 있고 ARIA엔 없는 비대칭이 있었다.
판단 GCM은 AEAD라 암호화·인증을 한 번에 처리 — 조합 실수 자체가 구조적으로 불가능. 두 구간 모두 AES-256-GCM으로 통일하기로 결정.
해결 ARIA-CBC+HMAC 구현·검증 경험은 코드를 지우지 않고 보존 + 별도 문서(ARIA_TO_AES_MIGRATION.md)로 남김. 마이그레이션 후 실제 실행으로 재검증(TLS 핸드셰이크 + AES-GCM 복호화 + 메트릭 정상 수신).
// 04
IPayloadSealer — 암호 방식을 세션과 분리
문제 세션(ApmSession/ResilientSender)이 특정 암호 구현에 고정되면, 위처럼 암호 방식을 바꿀 때마다 프레이밍·재연결 로직까지 손대야 한다.
판단 Seal()/Open() 인터페이스로 세션과 구체 암호 구현을 분리, 세션 생성 시점에 구현체만 주입.
해결 ARIA→AES 마이그레이션이 main.cpp 몇 줄(주입하는 구현체 교체)로 끝난 것 자체가 이 추상화의 값을 증명 — 세션/프레이밍/재연결 코드는 무변경.
// 05
메시지 프레이밍 + Protobuf 리플렉션
문제 전송 프로토콜에 메시지 경계가 없어, 한 번의 read를 메시지 하나로 가정하는 설계 공백이 있었다 — 우연히(작은 메시지) 동작했을 뿐.
판단 PacketHeader{size,id}로 프레이밍, 패킷 ID는 수동 배정 대신 Protobuf 리플렉션으로 자동 결정.
해결 PacketHandler::Register<T>()가 역직렬화까지 자동 처리 — ID 충돌·오타가 구조적으로 불가능.
// 06
IMetricStore — 컴파일 타임 저장소 선택
문제 SQLite(경량)와 TimescaleDB(시계열 특화) 둘 다 지원하고 싶지만, 안 쓰는 백엔드의 의존성이 남으면 "가벼운 에이전트"라는 목표에 어긋난다.
판단 런타임 분기 대신 인터페이스 + CMake 옵션(APM_STORAGE_BACKEND)으로 컴파일 타임에 하나만 선택.
해결 SQLite 선택 시 ldd로 libpq 미링크 실측 확인 — Postgres 미설치 환경에서도 빌드+실행 가능. 같은 문제를 .NET(APM_Console)은 두 프로바이더를 다 참조해도 빌드에 지장이 없어 런타임 선택으로 단순화 — 언어별 컴파일 모델 차이를 반영한 의도적 비대칭.
// 07
PrivilegeDrop — 최소 권한 원칙
문제 모니터링 에이전트가 침해당했을 때, 과도한 권한으로 실행 중이면 피해 범위가 커진다.
판단 포트 바인딩처럼 특권이 필요한 초기화만 root로 수행하고, 직후 setuid/setgid로 nobody까지 하향.
해결 gid→보조그룹 제거→uid 순서, 하향 후 setuid(0) 재시도 실패까지 방어적으로 검증.
// 08
도메인별 프로젝트 + Razor Class Library 플러그인
문제 Apm/Game 도메인을 한 프로젝트에 두면, 간헐적으로 진행되는 프로젝트 특성상 미래에 컨벤션을 잊고 다른 도메인 타입을 실수로 참조할 위험이 있다.
판단 공수가 더 들어도 컴파일 타임에 강제되는 진짜 도메인 격리를 우선 — 속도보다 구조 학습 가치를 선택.
해결 도메인별 Razor Class Library(.cshtml이 DLL에 내장) + 커스텀 AssemblyLoadContext로 런타임 로딩. 호스트가 이미 로드한 공유 계약 타입(IDomainModule 등)은 재로딩하지 않고 그대로 재사용하도록 처리 — 같은 이름의 타입도 ALC가 다르면 별개 타입으로 취급되는, .NET 플러그인 아키텍처의 잘 알려진 함정을 피함.
// 09
Windows 크로스플랫폼 포팅 + Smart App Control 대응
문제 Linux 전용으로 개발된 ResourceCollector(/proc 기반)·TCP 지표 조회(TCP_INFO)를 Windows에서 빌드하니 컴파일조차 안 됐고, 다 고쳐서 빌드에 성공한 뒤에도 실행 시 원인 불명으로 멈췄다.
판단 Windows 이벤트 로그(CodeIntegrity)로 추적한 결과 Smart App Control이 로컬에서 새로 빌드한(서명 안 된) vcpkg DLL 로딩 자체를 차단하고 있음을 확정 — 시스템 보안 설정을 낮추는 대신, 정적 링크로 전환해 서명 안 된 외부 DLL 의존성 자체를 없애기로 결정.
해결 WinAPI(GetSystemTimes/GlobalMemoryStatusEx/GetIfTable2/SIO_TCP_INFO)로 수집 로직 이식 + vcpkg x64-windows-static 트리플릿으로 재구성 — Collector.exe/Agent.exe가 외부 DLL 0개로 완전 정적 빌드되어 SAC 차단을 코드 변경 없이 우회. TLS+AES-GCM 통신·실측 리소스 수집·SQLite 저장까지 전체 파이프라인을 Windows에서 실제 실행으로 재검증.
// 10
테스트 전략 — 전체 커버리지 대신 핵심 위험 지점 우선
문제 포트폴리오 프로젝트는 시간 예산이 정해져 있다 — 모든 코드를 같은 강도로 테스트하는 건 "안 하는 것"과 실질적으로 같은 결과를 낳는다(어디에도 깊이가 없음).
판단 "실수하면 조용히 실패하고 파급력이 큰" 두 영역만 우선 — 암호화(AES-GCM 왕복/nonce/변조 거부)와 TCP 프레이밍(부분 수신 같은 비결정적 상황 재현). MetricsReceiverService의 private 로직은 인스턴스 필드 의존을 없애 파라미터 받는 static 메서드로 리팩터링(테스트 가능한 설계는 저절로 안 되고 의도적으로 만들어야 함).
해결 C++ GoogleTest 9개 + .NET xUnit 18개, 전부 통과. 테스트 없는 영역(예: 실제 소켓에 강결합된 프레이밍 재조립 로직)도 명확히 인지하고 우선순위상 미룬 것이라 설명 가능 — "빈틈이 없다"가 아니라 "빈틈을 알고 있다"는 게 요점.
// 11
Collector↔Console 관계 — 암묵적 전제를 명시적 네트워크 관계로
문제 초기엔 두 프로세스가 "같은 장비의 SQLite 파일을 각자 다른 시점에 연다"는 방식이었다 — 두 프로세스가 항상 같은 장비에 있어야만 동작하는, 암묵적이고 깨지기 쉬운 전제.
판단 Collector가 능동적으로 전송하고 Console이 자기 소유 DB에 저장하는 실제 네트워크 관계로 전환. 설정 파일을 평문 대신 JSON으로 택한 이유도 같은 맥락 — 지금은 로컬 파일이지만, 나중에 웹에서 이 설정(전송 주기 등)을 편집하게 될 가능성을 열어두려면 웹 쪽과 자연스럽게 주고받을 수 있는 포맷이 유리하다고 판단.
해결 stdin은 별도 스레드에서 읽고, 실제 전송은 asio::post()로 io_context 스레드에 위임 — 공유 상태(전송 큐 등)를 항상 단일 스레드에서만 건드리게 되어 락 자체가 불필요해지는 설계.
// Operational Features

"메트릭 수집기"에서 "APM"으로

시스템 리소스만 재는 걸 넘어, 운영 중 실제로 쓰는 4가지 기능을 순서대로 추가.

// 임계치 기반 알림
상태 전이 시에만 알림 (Zabbix/Nagios 방식)
문제 메트릭은 계속 쌓이는데, 이상 상황을 알아채려면 누군가 대시보드를 계속 보고 있어야 했다.
판단 임계치를 넘을 때마다가 아니라 상태가 바뀔 때(OK→Alert, Alert→Resolved)만 기록·알림 — 업계 표준 패턴. 임계치는 DB 저장+UI 편집(재배포 없이 조정), 현재 상태는 메모리 캐시가 아니라 매번 DB 재조회로 판단해 프로세스 재시작에도 상태가 안 깨지게 함.
해결 상태 전이 로직만 순수 함수(AlertEvaluator)로 분리해 단위테스트 대상으로 삼음. 이번 세션에 실제로 CPU 임계치를 실 트래픽보다 낮게 걸어, 알림이 열리고 화면에 렌더링되는 것까지 end-to-end로 재현·확인.
// 데이터 보존 정책
백엔드별로 다르게 구현, API는 하나로 통일
문제 저장소가 SQLite/TimescaleDB 두 종류인 데다, Collector 로컬 저장소와 Console 중앙 저장소까지 두 군데 — 어느 쪽이든 무한정 쌓이면 안 된다.
판단 TimescaleDB는 네이티브 add_retention_policy()로 청크째 드롭(거의 공짜), SQLite는 직접 DELETE+점진적 vacuum, Console(EF Core)은 백엔드 무관하게 ExecuteDeleteAsync 하나로 통일 — 저장소별 실제 구현은 다르게, 호출부는 똑같이.
해결 Metrics 30일 / 알림 이력 180일(사건 기록이라 더 길게). 실제 실행 검증 중 EF Core+SQLite 조합이 시간 비교를 SQL로 못 옮기는 버그를 발견해 수정(아래 "버그 발견" Bug #3 참고).
// 함수/트랜잭션 계측
RAII 스코프 기반 — "우리 APM으로 우리 자신을 계측"
문제 시스템 리소스만 재면 "모니터링"이지 "APM"이라 부르기엔 부족한데, 정작 계측할 함수/트랜잭션이 프로젝트 안에 없었다.
판단 별도 데모 앱 대신 이 프로젝트 자체 코드를 계측 — C++은 소멸자, .NET은 IAsyncDisposable로 같은 발상의 RAII API. Collector는 이미 있는 메트릭 전송 파이프라인을 그대로 재사용(새 포트 불필요), Console은 이미 자기 DB가 있어 네트워크 왕복 없이 직접 저장.
해결 Protobuf descriptor index가 C++/C# 양쪽에서 같은 값을 결정론적으로 생성한다는 점을 이용해, 패킷 타입 분기를 매직 넘버 없이 구현.
// 백분위/집계 통계
SQL 백분위 함수 없이 — 백엔드 무관 통일
문제 SQLite에는 PostgreSQL/TimescaleDB의 PERCENTILE_CONT 같은 SQL 백분위 함수가 없다 — 백엔드마다 로직이 갈리게 둘 순 없었다.
판단 시간 창으로 거른 span을 메모리로 가져와 C#에서 직접 계산(선형 보간, numpy.percentile 기본값과 동일한 정의) — 어느 백엔드든 완전히 같은 코드 경로.
해결 실제 실행 검증 중 "복합 인덱스가 이 쿼리에 맞는다"던 설계 당시 전제가, 실제로는 인덱스를 탈 수조차 없었다는 걸 발견(아래 "버그 발견" Bug #3와 같은 원인) — 설계 문서의 가정과 실제 동작이 다를 수 있음을 보여준 사례.
// Measured, Fixed, Re-measured

300 동시 접속까지 — 병목을 찾고 고치는 5라운드

자체 제작 LoadTester(실제 Agent와 같은 코드 경로로 in-process 다중 연결 시뮬레이션)로 매 라운드 재측정 — "고쳤다"고 끝내지 않고 다시 재는 것 자체가 이 과정의 핵심.

// Round 1 — 병목 찾기
72/100에서 하드 리밋
실측 100개 동시 접속을 요청했는데 72개만 성공, p95 지연시간 34초. strace -c로 원인 추적 — fdatasync/pwrite64가 syscall 시간의 70% 이상. SQLite 기본 저널링이 메트릭 1건마다 동기 flush를 걸고, 이게 네트워크 I/O와 같은 단일 이벤트 루프 스레드를 블로킹하고 있었다.
// Round 2 — 저장 비동기화
워커 스레드로 위임 — 첫 시도는 크래시
시행착오 기존 서브시스템(JobQueue)을 재사용했더니 재실측 중 10초 만에 반복 크래시 — 크로스 스레드로 쓰인 적이 한 번도 없어 드러나지 않았던 락 버그였다. 그 코드는 "여러 프로젝트에서 검증된 코드"라 손대지 않고, std::mutex/condition_variable만 쓰는 훨씬 작은 전용 큐로 교체.
결과 100/100 전원 접속 성공, p95/p99 사실상 0ms. 300-agent도 71→229로 3배 이상 개선.
// Round 3 — "사라졌다"는 착시
strace -f로 다시 보니, 비용은 그대로였다
발견 strace -c는 새로 생긴 워커 스레드를 추적하지 않는다 — "fdatasync가 안 보인다"를 "문제가 없어졌다"로 오독할 뻔했다. -f로 다시 재보니 같은 비용이 그대로 남아있었고(전체 syscall 시간의 25%), 그제서야 WAL 도입을 결정.
결과 fdatasync -97%, 그러나 WAL 공유메모리 락(fcntl)이 +437% — 비용이 사라진 게 아니라 fsync 비용이 락 비용으로 형태를 바꾼 트레이드오프.
// Round 4 — 다음 층의 병목
이번엔 콘솔 로깅이 1위
발견 300-agent 규모로 처리량이 늘자 std::cout << ... << std::endl(메트릭마다 강제 flush)이 write syscall 92%로 새 1위가 됨 — 병목은 한 층을 걷어내면 다음 층이 드러난다.
결과 로그 조립/출력을 전용 워커 스레드로 분리 + endl 대신 '\n' — 300개 전원(250→300) 접속 성공.
// Round 5 — 검증하다 새 버그
데이터 레이스 — 진단 코드 자체가 깨져서 나옴
발견 이 개선을 100-agent 규모에서 재확인하려고 스레드 ID를 직접 계측하다가, 그 진단 로그 자체가 스레드 간 문자 단위로 뒤섞여 나오는 걸 목격 — 성능을 위해 같이 넣은 sync_with_stdio(false)가 멀티스레드 안전장치를 없앤 게 원인이었다.
결과 남은 콘솔 출력도 전부 같은 워커로 위임해 "런타임 중 한 스레드만 스트림을 건드린다"는 원칙을 일관 적용. 수정 전/후 성능 지표를 다시 비교해 순수 정확성 버그였음을 확인(성능 영향 없음).

// Code Analysis

버그 발견 및 검증

제안 단계에서 완벽해 보였던 코드도, 실제 빌드·실행·렌더링 검증에서 발견된 문제들 — 그중 기술적으로 가장 깊었던 두 건(둘 다 동시성 버그, 300-agent 스케일 테스트 중 발견)은 원인 진단부터 해결 과정·재검증 결과까지 아래에 전 과정을 풀었다.

// Bug #1 — 공유 락 라이브러리의 소유권 버그, 크로스 스레드 첫 사용 10초 만에 전원 크래시
문제 — 저장 비동기화 재실측 6단계(1/10/50/100/100+ramp/300 에이전트) 전부, 기동 10초 만에 크래시

배경(Round 1 병목): strace -c로 확인한 원인은 SqliteMetricStore::Store()의 fdatasync가 네트워크 스레드(io_context.run()을 도는 유일한 스레드)를 매 메트릭마다 블로킹한다는 것 — 저장을 별도 워커 스레드로 위임하기로 하고, 이미 다른 프로젝트들에서 검증된 GW2_CrossPlatformCore/Thread/JobQueue를 재사용해 연결했다(빌드 성공, 단위테스트 9/9 통과).

재실측 중 크래시: 이 상태로 1-5와 동일한 6단계 부하 매트릭스를 재실행하자, 모든 단계에서 Collector가 기동 후 약 10초 만에 죽었다 (connect_fail이 agents=10부터 이미 발생, agents=1도 뒤늦게 크래시). "빌드+단위테스트 통과"와 "실제 부하 아래에서 동작"이 다르다는 걸 다시 확인한 지점.

결과적으로: 소유 스레드가 언락해도 락의 "소유자 ID" 비트가 그대로 남아 그 락을 처음 잡은 스레드가 영구 소유한 것처럼 보인다. 네트워크 스레드가 JobQueue::Push()에서 락을 한 번 잡았다 놓은 순간 락이 네트워크 스레드 소유로 영구 고정되고, 곧이어 워커 스레드가 Execute()→PopAll()에서 같은 락을 잡으려 하면 CAS가 계속 실패 → 10초(ACQUIRE_TIMEOUT_TICK) 스핀 후 CRASH("LOCK_TIMEOUT"). Lock/JobQueue는 APM_Agent에서 이번이 첫 크로스 스레드(네트워크→워커) 사용이라, 그동안 어느 프로젝트에서도 이 버그가 드러난 적이 없었다.

해결 — 공유 라이브러리는 안 건드리고, 자체 워커 큐로 의존 자체를 제거

판단: Lock.cpp는 "여러 프로젝트를 통해 이미 검증된 코드"라는 이유로 수정하지 않기로 결정 — 공유 라이브러리를 고치면 이 프로젝트가 확인하지 못한 다른 소비자까지 영향권에 들어간다. 대신 APM_Agent 쪽에서 std::mutex/condition_variable만 쓰는 전용 큐를 새로 만들어, JobQueue/Lock/ThreadManager 의존 자체를 걷어냈다. 

// Common/WorkerQueue.cpp — 표준 라이브러리 프리미티브만으로 같은 역할(단일 워커 스레드 순차 소비)
WorkerQueue::WorkerQueue()
    : _worker([this]() { WorkerLoop(); })
{
}

void WorkerQueue::Push(std::function<void()> job)
{
    {
        std::lock_guard<std::mutex> guard(_mutex);
        _jobs.push(std::move(job));
    }
    _cv.notify_one();
}

void WorkerQueue::WorkerLoop()
{
    while (true)
    {
        std::function<void()> job;
        {
            std::unique_lock<std::mutex> lock(_mutex);
            _cv.wait(lock, [this]() { return _stop || !_jobs.empty(); });
            if (_jobs.empty())  // _stop이어도 남은 job은 마저 비우고 종료
                return;
            job = std::move(_jobs.front());
            _jobs.pop();
        }
        job();
    }
}

문제 — 로그를 워커로 옮겨 병목을 해결했더니, 그 워커와 네트워크 스레드가 같은 스트림을 동시에 씀

배경(Round 4): 위 버그를 고쳐 300-agent 규모로 처리량이 늘자, 이번엔 PacketHandler::Register<apm::Metric> 안의 std::cout << ... << std::endl(메트릭 수신마다 강제 flush)이 write syscall 92%로 새 1위 병목이 됐다. 이 로그 조립·출력을 전용 consoleLogQueue 워커로 옮기고, std::endl→'\n'로 교체하면서 곁들여 std::ios::sync_with_stdio(false)(C stdio와의 동기화 해제, 순수 성능 이득)도 함께 켰다. 재측정 결과 connect_success가 250→300/300으로 개선.

그런데: 이 변경은 메트릭 수신 로그 한 줄만 워커로 옮겼을 뿐, accept 성공/실패, "WebServer로 N건 전송 시도"(메트릭/span 두 곳) 등 4곳의 std::cout/std::cerr 호출은 여전히 네트워크 스레드에 남아있었다 — 이제 네트워크 스레드와 콘솔 워커 스레드, 두 스레드가 같은 스트림을 동시에 건드리는 상황이 된 것. 원래 iostream은 기본적으로 C stdio와 동기화되어 있어 이게 우연히 스레드 안전성 비슷한 효과를 내고 있었는데, 방금 성능을 위해 켠 sync_with_stdio(false)가 바로 그 안전장치를 없앤 것이었다.

발견 계기: 100-agent 벤치마크 질문에 답하려고 스레드 ID를 로그에 직접 계측해서 넣었는데, 그 진단 로그 자체가 스레드 간 문자 단위로 뒤섞여서 나오는 것을 목격했다 — 레이스를 잡으려던 도구(로그)가 레이스 자체의 증거가 되어 스스로를 드러낸 셈. 

// 수정 전 — accept 성공/실패 로그가 네트워크 스레드에서 cout/cerr를 직접 씀
if (!ec)
{
    std::cout << "[Collector] connection accepted" << std::endl;
    // ...
}
else
{
    std::cerr << "[Collector] accept error : " << ec.message() << std::endl;
}
// → consoleLogQueue 워커 스레드가 "metric received" 줄을 찍는 동안,
//   네트워크 스레드가 이 줄을 동시에 찍으면 같은 std::cout 버퍼가 레이스로 깨짐
수정 — 남은 4곳도 전부 같은 워커로 위임, "런타임 중 정확히 한 스레드만 스트림을 만진다" 원칙을 일관 적용
if (!ec)
{
    // consoleLogQueue 워커 스레드 하나만 런타임 중 cout/cerr를 건드리도록 통일
    consoleLogQueue.Push([]() { std::cout << "[Collector] connection accepted\n"; });
    // ...
}
else
{
    std::string errMsg = ec.message();  // ec는 콜백 스코프 밖에서 죽을 수 있어 값으로 캡처
    consoleLogQueue.Push([errMsg]() { std::cerr << "[Collector] accept error : " << errMsg << '\n'; });
}
// "WebServer로 N건 전송 시도" 두 곳도 동일 패턴 — count/spanCount를 값으로 미리 캡처 후 위임
sync_with_stdio(false)는 유지(순수 성능 이득이라 없앨 이유가 없음), 레이스만 제거. 재검증 결과: 100-agent 스트레스 버스트(이전엔 재현 가능했던 조건)에서 깨진 로그 줄이 더는 발생하지 않음. 수정 전/후 성능 지표를 다시 비교해 순수 정확성 버그였음을 확인 — 100-agent p99 변화 없음(~2,050ms), 300-agent strace -f -c 총합도 오차범위 내(futex 57.78% vs 57.22%, 총 88.45s vs 86.09s). 이 재확인 과정에서 부수적으로 "100-agent 규모에서는 WAL+로깅 개선이 순효과가 거의 없고, 오히려 워커 스레드 동기화 오버헤드로 p99가 소폭(1,010ms→2,053ms) 늘어난다"는 것도 함께 확인 — 이 개선의 실질 효과는 300-agent 같은 고부하 구간에서만 뚜렷하다는 걸 실측으로 확정.
// Bug #3 — Razor HTML 인코딩이 JS 타임스탬프를 깨뜨림
문제 — 대시보드 차트가 초기 렌더링에서 빈 그래프로 뜸

서버에서 ISO 8601 문자열("o" 포맷, +09:00 시간대 오프셋 포함)을 그대로 JS 문자열 리터럴에 심었는데, Razor의 @ 표현식은 <script> 태그 안이라도 항상 HTML 인코딩을 거친다. +가 &#x2B;로 깨져 new Date(...)가 파싱 불가능한 문자열을 받게 된다. 실제 렌더링 결과를 curl로 확인하는 과정에서 발견. 

// 수정 전 - ISO 문자열을 그대로 JS 리터럴에 삽입
const initialPoints = [
@foreach (var m in Model.AsEnumerable().Reverse())
{
    <text>{ t: "@m.Ts.ToLocalTime().ToString("o")", cpu: @m.CpuUsagePercent.ToString("F1") },</text>
}
];
// → "+09:00"의 "+"가 "&#x2B;09:00"으로 인코딩되어 Date 파싱 실패
수정 — 유닉스 밀리초(숫자)로 전달
// 숫자는 인코딩할 특수문자가 없어서 이 문제 자체가 없음
const initialPoints = [
@foreach (var m in Model.AsEnumerable().Reverse())
{
    <text>{ t: @m.Ts.ToUnixTimeMilliseconds(), cpu: @m.CpuUsagePercent.ToString("F1") },</text>
}
];
// new Date(p.t)는 밀리초 숫자를 그대로 받으므로 이후 코드는 수정 불필요
설계 검토만으로는 잡히지 않고 실제 렌더링된 HTML을 눈으로 확인해야 발견되는 유형의 버그 — 이후 "실제 실행/렌더링으로 검증"을 모든 단계의 기본 절차로 삼는 계기가 됨.
// Bug #4 — TLS 핸드셰이크 모드 파라미터 누락 (미정의 동작)
문제 — Agent(client) 모드가 실질적으로 동작하지 않음

Collector(accept)만 있던 시절엔 핸드셰이크가 항상 server로 하드코딩돼 있었다. Agent(connect)가 추가되며 SessionMode를 도입했지만, 적용된 코드에서 생성자가 mode 파라미터를 받지 않아 _mode 멤버가 초기화 리스트에서 채워지지 않은 채 남아있었다(미정의 동작) — 게다가 handshakeType은 계산만 해두고 실제 async_handshake() 호출은 여전히 server를 그대로 썼다. 

// 발견 당시 - 생성자에 mode 파라미터가 없음
ApmSession::ApmSession(asio::ip::tcp::socket socket, asio::ssl::context& sslContext)
    : _sslStream(std::move(socket), sslContext)
    // _mode가 초기화 리스트에 없음 → 멤버는 선언돼 있지만 미정의 값
{
}

void ApmSession::DoHandshake()
{
    auto handshakeType = (_mode == SessionMode::Server)  // 미정의 _mode와 비교
        ? asio::ssl::stream_base::server
        : asio::ssl::stream_base::client;

    // handshakeType은 계산만 해두고 실제로는 안 씀 - server가 그대로 하드코딩
    _sslStream.async_handshake(asio::ssl::stream_base::server, /* ... */);
}
수정 — mode를 생성자로 전달받아 실제로 사용
enum class SessionMode
{
    Server,   // Collector 쪽 - accept로 받은 연결
    Client,   // Agent 쪽 - 밖으로 connect한 연결
};

ApmSession::ApmSession(asio::ip::tcp::socket socket, asio::ssl::context& sslContext, SessionMode mode)
    : _sslStream(std::move(socket), sslContext), _mode(mode)
{
}

void ApmSession::DoHandshake()
{
    auto self = shared_from_this();
    auto handshakeType = (_mode == SessionMode::Server)
        ? asio::ssl::stream_base::server
        : asio::ssl::stream_base::client;

    _sslStream.async_handshake(handshakeType,  // 계산한 값을 실제로 사용
        [this, self](const asio::error_code& ec) { /* ... */ });
}

// Bug #3 — EF Core + SQLite가 DateTimeOffset 비교를 SQL로 못 옮김
문제 — 알림 페이지를 처음 실행하자마자 앱 전체가 크래시

알림(2순위)·트레이스(5순위) 페이지는 빌드/단위테스트만 검증되고 실제로 브라우저에서 열어본 적이 없었다 — 이 프로젝트를 마무리하며 처음 실행해보니, 시작 직후 실행되는 보존 정책 백그라운드 서비스(RetentionService)의 db.Metrics.Where(m => m.Ts < cutoff).ExecuteDeleteAsync()가 InvalidOperationException으로 즉시 죽었다. Ts가 DateTimeOffset인데, 이 EF Core+SQLite 조합이 부등호 비교를 SQL로 아예 번역하지 못하는 게 원인 — ExecuteDeleteAsync뿐 아니라 일반 Where(...).ToListAsync()조차 똑같이 실패했다. 

// 수정 전 - DateTimeOffset 부등호 비교를 그대로 LINQ에 씀
var metricsCutoff = DateTimeOffset.UtcNow.AddDays(-_metricsRetentionDays);
var metricsDeleted = await db.Metrics
    .Where(m => m.Ts < metricsCutoff)
    .ExecuteDeleteAsync(ct);
// → InvalidOperationException: 이 LINQ 식을 SQL로 번역할 수 없음
수정 — LINQ 번역을 아예 거치지 않는 파라미터화 raw SQL
// LINQ 번역 자체를 우회 - 값은 파라미터 바인딩이라 인젝션 안전
var metricsDeleted = await db.Database.ExecuteSqlInterpolatedAsync(
    $"DELETE FROM Metrics WHERE Ts < {metricsCutoff}", ct);
수정 후 /apm/traces에서 같은 원인의 500 에러를 하나 더 발견 — 고친 즉시 "같은 패턴을 쓴 다른 코드가 더 있는가"를 능동적으로 재검색했고, 알림 컨트롤러는 동등 비교(== null)만 써서 이 버그의 영향을 안 받는다는 것도 함께 확인했다. 재빌드 후 클린 상태로 다시 띄워 크래시 없음을 확인하고, 임계치를 실제로 낮춰 알림이 열리고 렌더링되는 것까지 실 트래픽으로 재검증(dotnet test 18/18 통과, 회귀 없음).
