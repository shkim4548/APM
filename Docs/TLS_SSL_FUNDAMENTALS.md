> TLS/SSL 자체에 대한 기초 개념 정리. 실무 TLS/SSL 표준 참고서(Ivan Ristić, *Bulletproof SSL and TLS*)의 목차 구성을 참고해 구성함.
> 이 프로젝트의 구체적 구현(스크립트, 코드)은 `TLS_MECHANISM.md` 참고 — 이 문서는 "왜 TLS가 이렇게 생겼는가"에 대한 배경 지식이고, 그 문서는 "이 프로젝트가 그걸 어떻게 썼는가"에 대한 것.

## 1장. 암호학 기초 (TLS를 이해하기 위한 사전 지식)

### 1-1. 대칭키 암호 (Symmetric Cipher)
같은 키로 암호화·복호화를 모두 수행. 두 갈래로 나뉜다:
- **블록 암호(Block Cipher)**: 고정 크기 블록(예: 128비트) 단위로 처리. AES, ARIA가 여기 속함.
- **스트림 암호(Stream Cipher)**: 비트/바이트 단위로 연속 처리. ChaCha20 등.

블록 암호는 그 자체로는 "블록 하나"만 처리하는 방법이라, 여러 블록으로 된 실제 메시지를 어떻게 이어붙일지 정하는 **운용 모드(Mode of Operation)**가 따로 필요하다:
- **ECB**: 블록마다 독립적으로 암호화. 같은 평문 블록 → 같은 암호문 블록이 나와서 패턴이 노출됨(사실상 사용 금지).
- **CBC(Cipher Block Chaining)**: 이전 블록의 암호문을 다음 블록의 평문과 XOR 후 암호화. 매 메시지마다 다른 **IV(초기화 벡터)**가 필요. 무결성 보장이 없어 패딩 오라클 공격에 취약(6장 참고) — 이 프로젝트의 ARIA-CBC가 이 모드라, HMAC을 별도로 덧붙여 무결성을 보강한 이유가 여기 있음.
- **GCM(Galois/Counter Mode)**: 카운터 모드 암호화 + 인증 태그를 한 번에 처리하는 **AEAD(Authenticated Encryption with Associated Data)**. 암호화와 무결성 검증이 한 알고리즘 안에 통합돼 있어 CBC+HMAC처럼 두 단계를 손으로 조합할 필요가 없고, 조합 순서를 잘못 짤 위험 자체가 없음.

### 1-2. 공개키(비대칭) 암호 (Asymmetric Cipher)
수학적으로 짝을 이루는 **개인키**/**공개키** 쌍을 사용. 대표적으로:
- **RSA**: 소인수분해의 어려움에 기반. 암호화와 전자서명 둘 다 가능.
- **Diffie-Hellman(DH)**: 암호화가 아니라 **키 합의(key agreement)** 알고리즘 — 두 사람이 공개 채널로 메시지를 주고받는 것만으로 도청자는 모르는 공통 비밀값을 만들어낸다.
- **ECDH/ECDSA**: 타원곡선(Elliptic Curve) 기반의 DH/서명. 같은 안전성을 RSA보다 훨씬 짧은 키로 달성 — 현대 TLS의 사실상 표준.

### 1-3. 해시 함수와 MAC/HMAC
- **암호학적 해시 함수**(SHA-256 등): 임의 길이 입력 → 고정 길이 출력, 역산 불가능(일방향), 입력이 1비트만 달라도 출력이 완전히 달라짐(눈사태 효과).
- **MAC(Message Authentication Code)**: "이 메시지가 변조되지 않았고, 비밀키를 아는 사람이 만들었다"를 증명하는 값. 대칭키 기반.
- **HMAC**: 해시 함수를 이용해 MAC을 만드는 표준 구성법(`HMAC-SHA256` 등). 이 프로젝트의 Phase 3에서 ARIA-CBC 암호문에 대한 무결성 검증에 사용.

### 1-4. 전자서명 (Digital Signature)
공개키 암호의 응용 — 개인키로 서명, 공개키로 검증. "이 데이터를 이 개인키 소유자가 만들었다"는 것을 제3자도 검증 가능하게 함. 인증서 체인(4장)의 핵심 메커니즘.

### 1-5. 완전 순방향 비밀성 (Perfect Forward Secrecy, PFS)
장기 개인키(서버의 `.key` 파일)가 나중에 유출되더라도, **과거에 이미 주고받은 통신 내용은 여전히 안전**해야 한다는 속성. 매 세션마다 임시(ephemeral) DH 키 쌍을 새로 생성해서 세션 키를 합의하면(`DHE`, `ECDHE`), 그 임시 키를 세션이 끝난 뒤 폐기하는 순간 그 세션의 키를 복원할 방법이 사라짐 — 장기 개인키 유출과 무관해짐. TLS 1.3부터는 PFS 없는 키 교환 방식(고정 RSA 키 교환)이 아예 프로토콜에서 제거됨.

**이 프로젝트 연결점**: 1-1의 CBC/GCM 구분은 `AriaCipher`(CBC)와 `AesGcmCipher`(GCM)의 실제 클래스 분리로 대응됨 — `SESSION_LOG.md`의 "IPayloadSealer 일반화" 항목에서 두 모드를 하나의 인터페이스로 추상화한 이유가 바로 이 두 모드의 근본적 차이(별도 MAC 필요 여부) 때문.

## 2장. SSL/TLS 프로토콜의 역사와 버전

| 버전 | 연도 | 비고 |
|---|---|---|
| SSL 2.0 | 1995 | 심각한 설계 결함, 사실상 사용 금지 |
| SSL 3.0 | 1996 | POODLE 공격(2014)으로 완전히 폐기 |
| TLS 1.0 | 1999 | SSL 3.0의 후속(이름만 바뀜에 가까움). BEAST 공격에 취약 |
| TLS 1.1 | 2006 | BEAST 대응(명시적 IV) |
| TLS 1.2 | 2008 | AEAD(GCM) 도입, 해시 알고리즘 협상 가능 — 2020년대까지 가장 널리 쓰인 버전 |
| TLS 1.3 | 2018 | 핸드셰이크 전면 재설계(1-RTT), 취약한 알고리즘(RSA 키교환, CBC, MD5/SHA1) 프로토콜에서 완전 제거 |

**핵심 흐름**: 오래된 버전일수록 "일단 동작하게" 설계됐다가 실제 공격이 발견되며 패치가 누적됐고, TLS 1.3은 그 누적된 문제들을 프로토콜 차원에서 아예 선택지에서 지워버리는 방식(취약한 옵션 자체를 없앰)으로 재설계됨.

**이 프로젝트 연결점**: `ApmSession`이 OpenSSL의 `asio::ssl::context`를 통해 협상하는 버전은 기본적으로 OpenSSL 빌드 설정을 따름(별도로 버전을 강제 고정하지 않았다면) — 실무에서는 이 표를 근거로 TLS 1.2 미만은 명시적으로 비활성화하는 것이 표준 관행.

## 3장. TLS 프로토콜 상세 동작

### 3-1. 레코드 프로토콜 (Record Protocol)
TLS의 최하위 계층 — 상위 프로토콜(핸드셰이크/Alert/실제 데이터)을 일정 크기로 잘라 헤더(타입/버전/길이)를 붙이고, 협상된 암호로 감싸는 역할. 이 프로젝트의 `PacketHeader{size, id}` 프레이밍과 개념적으로 유사한 위치(다만 TLS 레코드는 TLS 자체의 것이고, `PacketHeader`는 그 위의 애플리케이션 계층 프레이밍).

### 3-2. 핸드셰이크 프로토콜 (TLS 1.2 기준, 2-RTT)
1. `ClientHello`: 클라이언트가 지원하는 TLS 버전, cipher suite 목록, 랜덤값 전송
2. `ServerHello`: 서버가 그중 하나를 선택 + 자기 랜덤값
3. `Certificate`: 서버가 인증서 체인 제시 (`server.crt`)
4. `ServerKeyExchange`/`ClientKeyExchange`: 키 합의에 필요한 값 교환(ECDHE의 공개값 등)
5. `Finished`(양쪽): 지금까지 핸드셰이크 메시지 전체의 해시를 방금 합의한 키로 암호화해서 교환 — 지금까지의 대화가 변조 없이 그대로 도착했음을 상호 확인

### 3-3. TLS 1.3 핸드셰이크 — 1-RTT로 단축
TLS 1.2가 "어떤 알고리즘을 쓸지 협상 → 그 다음 키 교환"의 2단계였다면, TLS 1.3은 클라이언트가 `ClientHello`에 자신이 가장 선호하는 키 교환 값을 **미리 추측해서 같이 보내는** 방식으로 왕복을 1회로 줄임(서버가 그 추측이 틀렸을 때만 예외적으로 재요청). 재접속 시엔 `0-RTT`(이전 세션 정보로 첫 요청부터 데이터 동봉)까지 가능하나, 재전송 공격(replay attack) 위험이 있어 멱등한 요청에만 권장됨.

### 3-4. Cipher Suite의 구성
TLS 1.2까지의 cipher suite 이름은 4개 요소의 조합이다. 예: `ECDHE-RSA-AES128-GCM-SHA256`
- `ECDHE`: 키 교환 알고리즘 (PFS 제공)
- `RSA`: 인증(서명) 알고리즘 — 서버가 자기 신원을 증명하는 방식
- `AES128-GCM`: 실제 데이터를 암호화하는 대칭 암호+모드
- `SHA256`: 핸드셰이크 무결성 검증용 해시

TLS 1.3은 키 교환/인증 알고리즘을 cipher suite 이름에서 분리하고, AEAD 암호+해시 조합만 남겨 단순화함(`TLS_AES_128_GCM_SHA256` 등).

### 3-5. 세션 재개 (Session Resumption)
매번 전체 핸드셰이크(특히 공개키 연산)를 다시 하는 건 비용이 크므로, 이전 세션의 키 정보를 짧게 캐싱해서 재접속 시 축약된 핸드셰이크만 하는 메커니즘. TLS 1.2는 `Session ID`/`Session Ticket` 방식, TLS 1.3은 PSK(Pre-Shared Key) 방식으로 통일.

### 3-6. Alert 프로토콜
핸드셰이크 실패, 인증서 검증 실패, 연결 종료 등을 상대에게 알리는 별도 채널. `close_notify`(정상 종료 신호) 없이 연결이 끊기면 "잘려나간 종료(truncation attack)"로 간주해야 하는 경우도 있음.

**이 프로젝트 연결점**: `ApmSession::DoHandshake()`가 `async_handshake`로 수행하는 게 3-2/3-3 과정 전체(OpenSSL이 내부적으로 처리, 애플리케이션 코드는 결과만 받음). `openssl s_client`로 검증했던 것(Phase 2-5)이 정확히 이 핸드셰이크가 끝까지 성공하는지를 눈으로 확인한 것.

## 4장. 공개키 기반구조 (PKI)

### 4-1. X.509 인증서 구조
표준화된 인증서 포맷. 주요 필드:
- **Subject**: 이 인증서가 누구의 것인가 (`CN=localhost` 같은 형태)
- **Issuer**: 누가 이 인증서에 서명했는가
- **Public Key**: 이 인증서가 보증하는 공개키
- **Validity**: 유효기간(`-days 365`가 여기 대응)
- **Signature**: Issuer가 위 내용 전체에 서명한 값

### 4-2. 인증기관(CA)과 신뢰 체인
실제 서비스에서는 브라우저/OS가 미리 신뢰하는 **루트 CA** 목록이 있고, 서버 인증서는 보통 "루트 CA → 중간 CA → 서버 인증서"의 체인으로 서명된다. 클라이언트는 이 체인을 끝까지 따라가 신뢰 루트에 도달하면 인증서를 신뢰한다.

**자체 서명(Self-signed) 인증서**는 이 체인이 없다 — Issuer와 Subject가 같다(자기가 자기에게 서명). 그래서 누구도 자동으로 신뢰하지 않고, 클라이언트가 예외적으로 이 인증서를 직접 신뢰 목록에 추가하거나 검증을 생략해야 함(`TLS_MECHANISM.md` 4장 참고).

### 4-3. 인증서 검증 절차 (클라이언트 관점)
1. 체인을 따라가며 각 서명이 유효한지 확인
2. 최종적으로 신뢰 루트에 도달하는지 확인
3. 유효기간(`Validity`) 내인지 확인
4. **폐기되지 않았는지** 확인(4-4)
5. `Subject`(또는 `SAN`)가 접속하려는 호스트명과 일치하는지 확인

### 4-4. 인증서 폐기 확인
개인키가 유출되는 등의 이유로 유효기간이 남았어도 신뢰를 철회해야 할 때 쓰는 메커니즘:
- **CRL(Certificate Revocation List)**: CA가 배포하는 폐기 목록 파일 — 클라이언트가 통째로 내려받아 대조.
- **OCSP(Online Certificate Status Protocol)**: 개별 인증서 하나에 대해 CA에게 실시간으로 "이거 아직 유효해?" 질의.
- **OCSP Stapling**: 매번 클라이언트가 CA에 물어보면 느리고 CA에 부하가 크므로, **서버**가 미리 CA로부터 받아둔 OCSP 응답을 핸드셰이크에 끼워 넣어 제공하는 최적화.

### 4-5. Certificate Transparency (CT)
발급된 모든 정식 인증서를 공개 로그에 기록하도록 강제하는 체계 — CA가 몰래(또는 실수로) 엉뚱한 인증서를 발급해도 공개 로그에서 나중에 발각되게 함. 최신 브라우저는 CT 로그에 없는 인증서를 신뢰하지 않음.

**이 프로젝트 연결점**: `server.crt`가 자체 서명이라 4-2의 신뢰 체인이 없음 — 그래서 `TLS_MECHANISM.md`가 "누구도 공식적으로 신뢰하지 않는다"고 명시한 것. 이 프로젝트는 포트폴리오/로컬 테스트 목적이라 4-4(폐기)/4-5(CT)는 해당 없음 — 실제 프로덕션 배포 시에는 필요해지는 항목.

## 5장. 실무 배포와 설정

### 5-1. Cipher Suite 선택 기준
- PFS를 제공하지 않는 스위트(고정 RSA 키교환) 배제
- CBC 모드보다 AEAD(GCM/ChaCha20-Poly1305) 우선
- 서버가 순서를 강제(`server cipher order`)해서 클라이언트가 약한 걸 고르는 걸 방지

### 5-2. 프로토콜 버전 지원 정책
TLS 1.0/1.1은 대부분의 표준(PCI-DSS 등)에서 이미 사용 금지 처리됨 — 최소 TLS 1.2, 가능하면 TLS 1.3 전용으로 구성하는 게 현재 표준 관행.

### 5-3. HSTS (HTTP Strict Transport Security)
"이 사이트는 앞으로 무조건 HTTPS로만 접속하라"고 브라우저에게 지시하는 응답 헤더. 최초 1회 평문 HTTP 요청조차 공격자가 가로챌 수 있는 위험(SSL Stripping)을 최소화.

### 5-4. 상호 인증 (mTLS, mutual TLS)
보통 TLS는 서버만 인증서를 제시하지만(서버가 클라이언트에게 자신을 증명), mTLS는 **클라이언트도 인증서를 제시**해서 서버가 클라이언트 신원까지 검증. 서버 간 통신(마이크로서비스, IoT 기기 인증 등)에서 흔히 쓰임.

**이 프로젝트 연결점**: 지금 구조는 일반 TLS(서버만 인증서 제시) — Agent/Collector는 "같은 신뢰 그룹 내부"라는 전제라 mTLS까지는 필요치 않다고 판단된 상태(현재까지 논의 기록 기준). 5-1/5-2는 실제 배포 단계에 재검토할 항목으로 남겨둘 만함.

## 6장. 알려진 공격과 취약점 (역사적 사례로 이해하는 "왜 이렇게 설계됐는가")

| 공격 | 대상 | 핵심 원리 | 결과적 대응 |
|---|---|---|---|
| **BEAST** (2011) | TLS 1.0의 CBC | 예측 가능한 IV를 이용해 평문 일부 추론 가능 | TLS 1.1+에서 명시적 랜덤 IV 의무화 |
| **CRIME/BREACH** | TLS/HTTP 압축 | 압축 후 길이 변화로 비밀 데이터(세션 쿠키 등)를 바이트 단위로 추론 | TLS 레벨 압축 비활성화가 표준 관행 |
| **Heartbleed** (2014) | OpenSSL 구현 버그(설계 결함 아님) | Heartbeat 확장의 길이 검증 누락으로 메모리 내용 유출(개인키까지 노출 가능) | 패치 + 전 세계 인증서 대량 재발급 사태 |
| **POODLE** (2014) | SSL 3.0의 CBC 패딩 검증 방식 | 패딩 오라클로 한 바이트씩 평문 복원 | **SSL 3.0 자체를 완전히 폐기**하는 계기가 됨 |
| **FREAK/Logjam** (2015) | 구식 "export cipher"(수출 규제 시절의 약한 키) 강제 다운그레이드 | 서버가 여전히 지원하던 옛날 약한 스위트로 협상을 유도 | export 등급 cipher suite 제거 |

### 6-1. 패딩 오라클(Padding Oracle) 공격 — 일반론
CBC 모드는 블록 끝을 채우는 패딩 규칙(PKCS#7 등)이 있는데, 서버가 "복호화는 됐지만 패딩이 틀렸다"는 응답과 "패딩은 맞는데 다른 이유로 실패했다"는 응답을 **구분해서 알려주면**, 공격자가 이 차이(오라클)를 반복 질의해 평문을 한 바이트씩 복원할 수 있다. **CBC 자체의 구조적 약점**이며, 이를 막는 표준 대응이 **Encrypt-then-MAC**(암호화 후 MAC을 검증해서 애초에 패딩 검사 단계까지 못 가게 함) 또는 애초에 AEAD(GCM 등, 패딩 개념 자체가 없음)로 바꾸는 것.

**이 프로젝트 연결점**: 6-1이 바로 이 프로젝트의 Phase 3 설계 근거 그 자체 — `README.md`에 "패딩 오라클과 Encrypt-then-MAC 대응"을 명시한 이유이자, `SecurePayload`가 "HMAC 검증 → 통과해야만 복호화 시도"의 순서를 강제한 이유. 또한 Collector→WebServer 구간에서 아예 GCM(AEAD)을 선택해 이 공격면 자체를 없앤 것도 6장 전체(특히 POODLE 사례)가 남긴 교훈("CBC+수동 MAC 조합은 순서를 잘못 짤 위험이 있으니, 가능하면 AEAD로 가라")의 실제 적용 사례.

## 7장. 이 프로젝트 전체 개념 매핑 표

| 이 프로젝트의 요소 | 관련 장 | 한 줄 설명 |
|---|---|---|
| `AriaCipher`(ARIA-CBC) | 1-1 | 블록 암호 + CBC 모드, 무결성은 별도 필요 |
| `HmacUtil`(HMAC-SHA256) | 1-3 | ARIA-CBC 암호문의 무결성 검증용 MAC |
| `SecurePayload`(Encrypt-then-MAC) | 6-1 | 패딩 오라클 공격 대응의 정석 패턴 |
| `AesGcmCipher`(AES-256-GCM) | 1-1, 6-1 | AEAD로 전환해 패딩 오라클 공격면 자체를 제거 |
| `server.key`/`server.crt` | 1-2, 4-1, 4-2 | 자체 서명 RSA 인증서 — 체인 없음, 수동 신뢰 필요 |
| `ApmSession::DoHandshake()` | 3-2, 3-3 | OpenSSL이 내부 수행하는 TLS 핸드셰이크 |
| `openssl s_client` 검증(Phase 2-5) | 3-2 | 핸드셰이크가 실제로 끝까지 성공하는지 확인 |
| ARIA 채택 이유(KISA 표준) | (배경) | TLS 기본 암호(AES 계열)와 별개로 국내 표준 대응 트랙 |
