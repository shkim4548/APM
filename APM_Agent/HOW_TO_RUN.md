# APM_Agent 실행 가이드

이 문서는 지금까지 만든 `Collector`/`Agent`를 처음부터 빌드하고 실행하는 방법만 다룬다.
설계 이유나 코드 내용은 `README.md`(포트폴리오 공개용 설명)와 `SESSION_LOG.md`(개발 이력)를 참고.

Linux(WSL 포함)와 Windows 둘 다 빌드+실행 검증됨(Windows는 2026-07-22 검증). 아래는 공통 절차 뒤에 OS별로 갈라지는 부분을 명시한다.

---

## 1. 사전 준비물 (한 번만 설치)

### Linux

```bash
sudo apt install build-essential cmake libssl-dev protobuf-compiler libprotobuf-dev libsqlite3-dev
```

| 패키지 | 왜 필요한가 |
|---|---|
| `build-essential`, `cmake` | 컴파일러/빌드 시스템 |
| `libssl-dev` | TLS(`asio::ssl`), AES-GCM(OpenSSL EVP API) |
| `protobuf-compiler`, `libprotobuf-dev` | `.proto` 파일을 `.pb.h`/`.pb.cc`로 컴파일(`protoc`) + 런타임 라이브러리 |
| `libsqlite3-dev` | 기본 저장소 백엔드(SQLite) |

TimescaleDB 백엔드를 쓸 경우에만 추가로 `libpq-dev`(PostgreSQL 클라이언트)와 로컬 Postgres+`timescaledb` 확장이 필요하다 — 기본값(SQLite)은 이게 전혀 없어도 된다.

### Windows

| 준비물 | 비고 |
|---|---|
| Visual Studio 2022(Community 이상), "C++를 사용한 데스크톱 개발" 워크로드 | CMake/Ninja가 번들되어 있으나, **번들 vcpkg(`VC\vcpkg`)는 classic 패키지 설치를 지원하지 않는 제한된 배포판**이라 그대로 못 씀(아래 참고) |
| 독립 vcpkg 인스턴스 | `git clone https://github.com/microsoft/vcpkg.git` 후 `bootstrap-vcpkg.bat` 실행 |
| Git Bash (Git for Windows에 포함) | 인증서/키 생성 셸 스크립트(`.sh`) 실행 및 `openssl` CLI 제공용 |

```powershell
git clone https://github.com/microsoft/vcpkg.git D:\Dev\vcpkg
D:\Dev\vcpkg\bootstrap-vcpkg.bat
D:\Dev\vcpkg\vcpkg.exe install openssl:x64-windows-static protobuf:x64-windows-static sqlite3:x64-windows-static gtest:x64-windows-static
```

`x64-windows`(동적 링크)가 아니라 **`x64-windows-static`**로 설치하는 이유는 3-2절 참고(Smart App Control 대응).

## 2. 최초 1회 설정 — 키/인증서 생성

`APM_Agent/` 디렉토리 안에서 실행(Linux/Windows 공통, Windows는 Git Bash 사용):

```bash
cd APM_Agent
bash certs/generate_test_cert.sh              # TLS용 자체 서명 인증서 (server.crt, server.key)
bash certs/generate_agent_collector_key.sh    # Agent↔Collector AES-256-GCM 키 (agent_collector_aes.key)
bash certs/generate_webserver_key.sh          # Collector↔APM_Console AES-256-GCM 키 (webserver_aes.key)
```

생성된 파일은 `certs/` 안에 남고, `.gitignore`에 이미 걸려 있어 커밋되지 않는다. **이 스크립트는 딱 한 번만 실행하면 된다** — `Collector`와 `Agent`가 같은 `certs/` 폴더를 보고 실행되므로 다시 생성할 필요 없음(다시 생성하면 기존 연결 상대방과 키가 안 맞아서 통신이 끊긴다).

> `certs/generate_payload_keys.sh`(ARIA/HMAC 키)는 과거(Agent↔Collector가 ARIA-256-CBC+HMAC이던 시절) 스크립트로, 지금 실행 경로에서는 쓰이지 않는다(`AriaCipher`/`HmacUtil`/`SecurePayload` 코드 자체는 참고용으로 남아있음 — `Docs/ARIA_TO_AES_MIGRATION.md` 참고). 지금은 위 3개 스크립트만 실행하면 된다.

**Windows에서 주의**: Git Bash는 `/`로 시작하는 인자를 파일 경로로 오인해서 변환하는 문제(MSYS path conversion)가 있다. `openssl req -subj "/CN=localhost"` 같은 명령을 직접 칠 때는 `MSYS_NO_PATHCONV=1`을 앞에 붙일 것(위 스크립트들은 이미 이 문제를 겪지 않는 인자 구성이라 그냥 실행하면 됨).

## 3. 빌드

### Linux

```bash
cd APM_Agent
cmake -B build -S . -DAPM_STORAGE_BACKEND=SQLite   # 저장소 기본값. TimescaleDB로 바꾸려면 여기만 교체
cmake --build build -j$(nproc)
```

빌드가 끝나면 `APM_Agent/build/` 안에 실행 파일 두 개가 생긴다: `Collector`, `Agent`.

코드를 수정한 뒤에는 `cmake --build build -j$(nproc)`만 다시 실행하면 됨(재구성 불필요, 소스 파일이 새로 추가된 경우에만 `cmake -B build -S .`부터 다시).

### Windows

```powershell
cd APM_Agent
cmake -B build-static -S . `
    -DCMAKE_TOOLCHAIN_FILE=D:/Dev/vcpkg/scripts/buildsystems/vcpkg.cmake `
    -DVCPKG_TARGET_TRIPLET=x64-windows-static `
    -DCMAKE_MSVC_RUNTIME_LIBRARY="MultiThreaded$<$<CONFIG:Debug>:Debug>" `
    -G "Visual Studio 17 2022" -A x64
cmake --build build-static --config Debug
```

빌드가 끝나면 `APM_Agent/build-static/Debug/`에 `Collector.exe`/`Agent.exe`가, `APM_Agent/build-static/tests/Debug/`에 `APM_Common_Tests.exe`가 생긴다. **외부 DLL 의존성 없이 완전 정적으로 빌드됨**(이유는 3-2절).

**주의(1회성, 이미 반영됨)**: 저장소의 `Metric.pb.h`/`.pb.cc`는 Linux protobuf 버전으로 생성돼 있어서, vcpkg가 설치한 최신 protobuf와 버전이 다르면 `error C1189: This file was generated by a newer version of protoc`가 난다. 이 경우 vcpkg가 함께 설치한 `protoc.exe`로 재생성:
```powershell
cd APM_Agent\Protocol
D:\Dev\vcpkg\installed\x64-windows\tools\protobuf\protoc.exe --cpp_out=. Metric.proto
```
(재생성 후 Windows에서 계속 작업한다면 다시 겪지 않지만, 이후 Linux에서 빌드하면 반대 방향으로 같은 문제가 재발할 수 있다 — 그땐 Linux `protoc`으로 다시 재생성.)

## 4. 실행

**반드시 `APM_Agent/` 디렉토리 안에서 실행할 것** — `certs/server.crt`, `certs/agent_collector_aes.key` 등을 상대경로로 찾기 때문에 다른 위치에서 실행하면 "파일을 찾을 수 없음" 에러가 난다.

### Linux

**터미널 1 — Collector(수집 서버)를 먼저 실행:**
```bash
cd APM_Agent
./build/Collector
```
**터미널 2 — Agent(수집 에이전트)를 그다음 실행:**
```bash
cd APM_Agent
./build/Agent
```

### Windows

**터미널 1 — Collector:**
```powershell
cd APM_Agent
.\build-static\Debug\Collector.exe
```
**터미널 2 — Agent:**
```powershell
cd APM_Agent
.\build-static\Debug\Agent.exe
```

### 공통 — 정상이면 이렇게 뜬다

`Collector`:
```
[PrivilegeDrop] 이미 비-root 권한으로 실행 중 - 하향 불필요        (Linux)
[PrivilegeDrop] Windows에서는 미지원(설계상 범위 밖) - 스킵         (Windows)
Collector listening on port 9000 (TLS)
```

`Agent`:
```
[ResilientSender] connected
[ResilientSender] TLS handshake complete
[ResilientSender] queued (size=1)
```

**Collector를 먼저 켜야 하는 이유**: `Agent`는 시작하자마자 `Collector`(127.0.0.1:9000)로 접속을 시도한다. `Collector`가 아직 안 떠 있으면 `connect failed`가 찍히지만(Windows 콘솔에서는 시스템 에러 메시지가 코드페이지 문제로 깨져 보일 수 있음 — 기능상 문제 아님), `Agent`는 5초마다 자동으로 재시도하므로 순서가 바뀌어도(먼저 `Agent`를 켜도) 크래시 없이 나중에 `Collector`가 뜨면 알아서 연결된다.

## 5. 정상 동작 확인

`Collector`를 실행한 터미널에 5초 간격으로 이런 로그가 계속 찍히면 정상이다:

```
[Collector] connection accepted
[Collector] metric stored: cpu=1.3% mem=.../... disk=.../... net=rx:...B/s,tx:...B/s tcp=rtt:...us,...
```

- `cpu=`/`mem=`/`disk=`: 5초마다 새 값으로 갱신되면 실제로 수집이 되고 있는 것
- `metric stored`: SQLite(`apm_metrics.db`)에 실제로 저장까지 됐다는 뜻

**DB에 실제로 쌓였는지 직접 확인하고 싶다면** (`sqlite3` CLI가 없는 환경이라 Python으로, Linux/Windows 공통):
```bash
cd APM_Agent
python3 -c "
import sqlite3
conn = sqlite3.connect('apm_metrics.db')
for row in conn.execute('SELECT * FROM metrics ORDER BY ts DESC LIMIT 5;'):
    print(row)
"
```

## 6. 종료

- **Linux**: 각 터미널에서 `Ctrl+C`.
- **Windows**: 각 콘솔 창에서 `Ctrl+C`, 또는 `taskkill /F /IM Collector.exe`/`taskkill /F /IM Agent.exe`.

`Collector`를 먼저 죽여도 `Agent`는 죽지 않고 재연결을 계속 시도하며, 그동안 수집한 메트릭을 메모리 큐에 버퍼링해뒀다가 `Collector`가 다시 뜨면 순서대로 재전송한다(최대 100건, 그 이상은 오래된 것부터 버림).

## 7. 단위 테스트

```bash
# Linux
./build/tests/APM_Common_Tests

# Windows
.\build-static\tests\Debug\APM_Common_Tests.exe
```
9개 전부 통과(`AesGcmCipher` 5개 + `AesGcmPayload` 4개)해야 정상. `APM_BUILD_TESTS=OFF`로 빌드했거나 GTest를 못 찾은 환경(Linux에서 `libgtest-dev` 미설치, Windows에서 vcpkg에 `gtest` 미설치)이면 이 실행 파일 자체가 없다.

## 8. 자주 하는 실수

| 증상 | 원인 | 해결 |
|---|---|---|
| `cannot open ... certs/server.crt` | `APM_Agent/` 밖에서 실행함 | `cd APM_Agent` 하고 실행 |
| `[ApmSession] payload verify/decrypt failed` | `Collector`/`Agent`가 서로 다른 `agent_collector_aes.key`를 보고 있음 | 키를 다시 생성했다면 두 프로세스 다 재시작(같은 `certs/` 폴더를 봐야 함) |
| `Address already in use` (Collector 기동 실패, Linux) / `bind: 주소가 이미 사용 중` (Windows) | 이미 다른 `Collector`가 9000번 포트를 쓰고 있음 | Linux: `pgrep -af build/Collector`로 찾아서 `kill`. Windows: `tasklist \| findstr Collector`로 PID 확인 후 `taskkill /F /PID <pid>` |
| `find_package(SQLite3)` 실패 (cmake 단계, Linux) | `libsqlite3-dev` 미설치 | 위 1번 "사전 준비물(Linux)" 참고 |
| `error: Could not locate a manifest... does not have a classic mode instance` (vcpkg install, Windows) | VS2022 번들 vcpkg(`VC\vcpkg`)로 설치 시도함 — 이 배포판은 classic 패키지 설치 미지원 | 별도로 `git clone`한 독립 vcpkg 인스턴스 사용(위 1번 "사전 준비물(Windows)") |
| `error C1189: This file was generated by a newer version of protoc` (Windows) | 저장소의 `Metric.pb.h`/`.pb.cc`가 Linux protobuf 버전으로 생성돼 있어 vcpkg 설치 protobuf와 버전 불일치 | 3번 "빌드(Windows)"의 `protoc --cpp_out=.` 재생성 명령 참고 |
| `TCP_INFO_v0`/`SIO_TCP_INFO`: '선언되지 않은 식별자입니다' (Windows) | `_WIN32_WINNT` 미정의 시 asio가 Windows 7을 기본 타겟으로 가정, Windows 10 전용 API가 SDK 헤더에서 숨겨짐 | `pch.h`에 이미 `#define _WIN32_WINNT 0x0A00`(asio.hpp include 전) 반영됨 — 이 문서 기준 최신 코드라면 재발 안 함 |
| GTest 한글 테스트 이름이 깨지며 100개+ 컴파일 에러(Windows) | MSVC가 UTF-8 소스를 시스템 코드페이지(949)로 잘못 해석 | `APM_Agent/CMakeLists.txt`에 이미 `/utf-8` 옵션 반영됨 — 재발 안 함 |
| `Agent.exe`/`Collector.exe`가 실행 시 응답 없이 멈추거나 즉시 종료(Windows) | Windows 11 **Smart App Control**이 로컬 빌드(서명 안 된) vcpkg 동적 DLL 로딩을 차단(이벤트 뷰어의 `Microsoft-Windows-CodeIntegrity/Operational` 로그로 확인 가능) | `x64-windows`(동적) 대신 `x64-windows-static`(정적) 트리플릿으로 재구성 — 외부 DLL 의존성 자체가 없어져서 우회됨(위 1, 3번 Windows 절 참고). 시스템 보안 설정(SAC)은 끄지 않는 것을 권장 |
