10-3. io_context — 작동 원리

10-1/10-2의 모든 화살표가 실제로는 이 루프 하나 위에서 등록→대기→콜백 실행을 반복한 결과. Agent/Collector/LoadTester 전부 프로세스당 1개, run()을 부른 스레드 하나에서만 동작.
A. run() 루프 자체
ready queue에 실행 대기 중인 핸들러가 있는가?
이벤트가 이미 발생했거나 post()로 직접 밀어넣어진 핸들러
있음 → 하나 꺼내 이 스레드 위에서 즉시 실행
없음 → epoll_wait(timeout) 진입
timeout = 가장 가까운 타이머 만료 시각. 이 구간에서 스레드는 실제로 잠듦(sleep) — busy-wait 아님
epoll_wait가 깨어나면: 준비된 fd/타이머 → 각각의 완료 핸들러로 변환해 ready queue에 적재
↺ 다시 루프 처음(ready queue 확인)으로 — 미결 작업 수 0이 될 때까지 반복(§2: 사실상 절대 0 안 됨)
B. 실제 체이닝 예시 — ResilientSender::Connect()
async_resolve(host, port, 콜백A)
Common/ResilientSender.cpp
등록만 하고 즉시 리턴 — 스레드는 A로 돌아가 다른 세션 이벤트 처리 가능
DNS 응답 옴 → 콜백A가 ready queue에 들어가 실행
↓
콜백A 안에서: async_connect(socket, endpoints, 콜백B)
TCP 3-way handshake 완료 → 콜백B 실행
↓
콜백B 안에서: ApmSession 생성 → Start() → DoHandshake()
Common/ApmSession.cpp
_sslStream.async_handshake(..., 콜백C) — TLS 핸드셰이크도 내부적으로 async_read/write 여러 번을 체이닝(OpenSSL BIO를 io_context가 구동)
TLS 핸드셰이크 완료 → 콜백C 실행
↓
콜백C 안에서: _onReady() → RegisterRecv() → async_read_some(..., 콜백D)
자기 자신을 재무장(re-arm) — §2 "자연 종료 불가 콜백" 패턴과 동일
데이터 도착 → 콜백D 실행 → ProcessAccumulated() → RegisterRecv() 재호출
↺ 콜백D가 스스로를 다시 등록 — 이후 무한 반복
  • 화살표 하나 = 한 사이클 — 콜스택이 계속 깊어지는 게 아니라, 매 핸들러가 실행되고 리턴하면 스레드는 다시 A의 ready queue 확인으로 돌아감. DNS/TCP/TLS 왕복에 걸리는 실제 시간 동안 이 스레드는 다른 세션의 이벤트를 처리할 수 있음.
  • 타이머도 같은 대기에 얹힘 — _reconnectTimer.async_wait(...)(Common/ResilientSender.cpp), Collector의 pushTimer/pruneTimer 전부 별도 스레드가 아니라 A의 epoll_wait(timeout) 인자로 만료 시각이 들어가는 방식 — I/O 대기와 타이머 대기가 syscall 한 번으로 동시 처리됨.
  • asio::post의 스레드 간 웨이크업 — 10-2의 cliThread가 asio::post(ioContext, flushToWebServer)를 부르면, io_context 스레드가 A에서 epoll_wait에 잠들어 있어도 asio 내부 wake-up fd가 그 대기를 강제로 깨워 ready queue의 핸들러를 다음 차례로 실행시킴 — 소켓 이벤트 없이도 실행을 이 스레드로 넘기는 통로.
  • self = shared_from_this() 캡처 이유 — 콜백이 등록된 시점부터 실제 실행되는 시점 사이 그 객체(예: ApmSession)는 io_context 내부에 "대기 중"으로 붙잡혀 있음. 그 사이 다른 참조가 다 사라져도 소멸되면 안 되므로 콜백 안에 shared_ptr을 같이 캡처해 생존을 보장.

10-4. 다음 분석 순서 메모

  1. 수집 항목별 기능 분석 — 10-1의 CPU/메모리/디스크/네트워크/TCP를 항목별로 나눠 Linux /proc 파싱 방식과 Windows WinAPI 방식을 짝지어 비교. "왜 이 값을 이렇게 계산하는가"(예: CPU/네트워크는 왜 델타 계산이 필요한가)가 여기서 드러남.
  2. LoadTester 분석 — APM_Agent/LoadTester/로 이동해 "Agent인 척하는 코드가 실제 프로토콜/큐잉 로직을 어떻게 재사용하는지" 확인. 프로토콜을 소비자 관점에서 재검증하는 목적.
